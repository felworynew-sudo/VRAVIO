# ТЗ: векторная часть VRAVIO

Документ описывает, как из нынешнего векторного редактора — шести инструментов
поверх плоского списка фигур — сделать среду уровня Illustrator, не сломав того,
что уже работает, и не заведя вторую модель документа рядом с ядром.

Язык документа — русский, идентификаторы и имена файлов — английские, как во
всём репозитории. Правила работы — те же, что в `CLAUDE.md`: расширение файлом,
а не веткой; единственная дверь; объявленная опция обязана влиять на результат;
каждая проверка доказана падающей, когда ломаешь то, что она стережёт.

**Как пользоваться.** Каждый этап заканчивается состоянием, в котором проект
собирается, проходит тесты и работает. Между этапами можно остановиться на любой
срок. Отмечайте выполненное прямо здесь: `- [x]`. Строка закрыта, только когда
есть и реализация, и автопроверка.

## 2. Что сломано или отсутствует. Измерено, а не предположено

### 2.1. Габарит пути считается неверно — подтверждено прогоном

`shapeBounds` для пути делает `Math.min(...xs, 0)`. Ноль в списке означает, что
габарит **всегда растягивается до начала координат**.

Проверено: путь 100×100, нарисованный в точке (500, 500), отдаёт габарит
`{x: 0, y: 0, width: 600, height: 600}`. То есть рамка выделения в шесть раз
больше фигуры, а попадание курсором срабатывает по всему левому верхнему углу
документа.

Вторая ошибка там же: габарит считается по опорным точкам и **игнорирует ручки
Безье**. Кривая, выпирающая за свои опорные точки, обрезается.

### 2.2. Попадание курсором — по прямоугольнику габарита

`hitTestShape` проверяет только прямоугольник. Клик в дырку буквы «О» выделяет
её; клик далеко от тонкой диагональной линии выделяет её же. Настоящего
попадания по заливке и по обводке нет.

### 2.3. Габарит текста выдуман

`width: Math.max(40, value.length * fontSize * .55)`. Это не измерение, а
формула. При этом настоящее измерение в проекте **уже есть** — `textRender.ts`
пользуется `measureText` для растрового текста. Векторный текст просто не
подключён к нему.

### 2.4. Нет трансформации как таковой

У прямоугольника и эллипса есть `rotation`, у пути и текста нет ничего. Нет
матрицы, нет наследования преобразования, нет масштабирования группы.

### 2.5. Нет групп и вложенности

`shapes` — плоский массив. Ни группы, ни слоя, ни артборда как контейнера.

### 2.6. Нет булевых операций, офсета, упрощения, обводки в контур

Ни объединения, ни вычитания, ни пересечения, ни «преобразовать обводку в
объект».

### 2.7. Нет градиентов, паттернов, множественных заливок и обводок

`VectorStyle` — это `fill: string | null`, `stroke`, `strokeWidth`, `opacity`.
Ни градиента, ни пунктира, ни концов линии, ни соединений, ни режимов наложения.

### 2.8. Нет привязок

Ни к сетке, ни к направляющим, ни к узлам, ни к пересечениям, ни к центрам.

### 2.9. Поиск фигуры под курсором — линейный

`shapeAt` перебирает весь массив на каждое движение мыши. Пространственного
индекса нет.

### 2.10. Рендер — по DOM-узлу на фигуру

`VectorWorkspace` рисует `<svg>` с React-элементом на каждую фигуру. Это
правильный первый выбор — браузер отлично умеет SVG, — но у него есть потолок:
несколько тысяч узлов, и панорамирование начинает заикаться. Потолок надо
**измерить**, а не угадать (этап 1).

### 2.11. Нет импорта и экспорта SVG

Единственное, что умеет File > Open с `.svg`, — растеризовать его как картинку.
Векторный SVG внутрь документа не попадает, и обратно документ не выгружается.

### 2.12. Нет недеструктивности

Нарисовал прямоугольник, скруглил углы, применил офсет — и остался безымянный
путь из сорока семи точек. Исходный прямоугольник исчез.

## 3. Решения архитектуры

### 3.1. Недеструктивность — не функция, а форма объекта

Ключевое решение всего документа. Объект хранит **источник** и **стопку
модификаторов**, а не результат:

```
VectorEntity {
  id, name, visible, locked
  source:      Rectangle | Ellipse | Path | Text | Image | Group
  transform:   Matrix
  geometry:    GeometryModifier[]   // офсет, скругление, упрощение, булева
  appearance:  Appearance[]         // заливки, обводки, тени — стопкой
  clip:        ClipSource | null
}
```

Прямоугольник со скруглением 20, офсетом +10 и тремя обводками остаётся
**прямоугольником**: ширину, высоту и радиус можно править после всего.

Отсюда техническое требование: результат вычисления стопки кешируется, а не
пересчитывается на каждый кадр, и инвалидируется по номеру ревизии — тот же
приём, которым уже пользуются ассеты ядра.

**Каждый модификатор — файл в каталоге** (`geometry/definitions/offset.ts`), как
инструменты и команды. Добавление модификатора не должно править ни одной
существующей строки — правило 6 из `CLAUDE.md`.

### 3.2. Граница TypeScript / Rust — не сразу, но спроектированная заранее

Предложение вынести геометрию в Rust/WASM правильное, но **не первым шагом**.

Сейчас векторного кода 1 211 строк, и он не описывает даже групп. Начать с
переноса математики в Rust — значит закрепить в более сложном языке модель,
которая ещё не сложилась, и обзавестись WASM-сборкой раньше, чем появится, что
в неё класть. При этом семантические дыры из раздела 2 — группы, трансформации,
настоящие метрики текста — это **не математика**, их Rust не чинит.

Порядок такой:

1. Этапы 2–6 чинят семантику и делают её измеримой — на TypeScript.
2. Этап 7 вводит **один порт** `VectorGeometryPort` с реализацией на TS
   (медленной, но эталонной) и на WASM (быстрой). Одна дверь, две реализации,
   один набор тестов на обе — тогда «WASM даёт то же самое» становится
   утверждением, которое проверяется, а не надеждой.

Rust-инструментарий на машине уже стоит — его привёз этап 12 основного плана
(Tauri). Цена входа в WASM для этого проекта уже уплачена.

Граница проходит так: **TypeScript — интерфейс, инструменты и смысл документа;
WASM — тяжёлая геометрия без состояния**. Порт принимает и отдаёт плоские
массивы чисел, а не объекты документа. Отсутствие состояния — и есть то условие,
при котором вторая реализация не разъедется с первой.

### 3.3. Рендер за абстракцией, выбор бэкенда по измерению

```
interface VectorRenderer { render(scene, viewport): void }
```

- **SVG-DOM** — нынешний. Остаётся: даёт бесплатно сглаживание, текст,
  доступность и отладку через инспектор браузера.
- **Canvas 2D** — второй, через `Path2D` из уже существующего `pathData`.
- **GPU** — третий, и только если замеры покажут, что нужен.

Переключение — по измеренному порогу числа объектов, а не по вкусу. Порог
попадает в этот документ цифрой после этапа 1.

### 3.4. Модель документа остаётся своей

Ни Paper.js, ни Graphite не становятся хозяином документа. У VRAVIO уже есть
`Kernel`, `Document`, `Assets`, `History`, круговой обмен, и вторая модель рядом
означала бы вечную синхронизацию двух деревьев. Доноры поставляют **алгоритмы и
решения**, а не владение состоянием.

### 3.5. SVG — формат обмена, а не внутреннее представление

```
SVG → импорт → семантическая модель VRAVIO → экспорт → SVG
```

Внутренняя модель богаче SVG (недеструктивные модификаторы, стопки оформления),
и попытка сделать документ SVG-деревом сразу отрезала бы всё из раздела 3.1.

### 3.6. Совместимость документов

`schemaVersion` растёт 2 → 3, миграция пишется вместе с изменением модели и
проверяется тестом на документе прошлой версии. Ни один сохранённый документ не
должен перестать открываться.

Три предупреждения, которые стоило записать до начала работы:

- **Clipper2 работает с полигонами, не с кривыми** — это сказано в его же
  описании. Значит цепочка `Безье → спрямление → Clipper → полигоны → обратная
  аппроксимация в кривые`. Первое надёжное решение это даёт; результата уровня
  Illustrator, где после объединения остаются гладкие кривые с малым числом
  узлов, — ещё нет. Обратная аппроксимация — отдельная задача этапа 8.
- **У Lyon нет встроенного сглаживания**, это прямо написано в его FAQ. Если
  дойдём до GPU, сглаживание — наша забота.
- **Vello его авторы называют экспериментальным**, а поддержка браузера через
  WebGPU в его описании не заявлена. Поэтому он в плане стоит последним и с
  правом не делать этот этап вовсе.
- Код Inkscape — GPL. Пользоваться им как справочником о том, какие функции
  нужны, — одно; переносить оттуда код дословно — другое, это меняет лицензию
  VRAVIO. В плане он значится только как перечень возможностей.

## 5. Этапы

### Этап 1. Измерить нынешнее и застолбить пол — сделано 5 сентября 2026

Цель: цифры, ниже которых нельзя опускаться, и подтверждённый потолок рендера.

- [x] Замер: сколько объектов держит нынешний SVG-рендер при плавном
      панорамировании — искать порог, где кадр превышает 16 мс
- [x] Замер: время `shapeAt` на 100 / 1 000 / 10 000 фигур
- [x] Замер: время открытия и автосохранения документа на 1 000 фигур
- [x] Тест-пол `packages/env-vector/src/performance.bench.test.ts` по образцу
      растрового, с той же оговоркой про нагрузку машины из `CLAUDE.md`
- [x] Тест, фиксирующий баг 2.1 как **ожидаемо неверный** результат, чтобы этап
      3 сломал именно его — `vector.test.ts`, «path bounds stretch to the
      origin»

**Метод — тот же урок, что уже был записан в `CLAUDE.md` про измерение через
`requestAnimationFrame`.** Первая попытка мерить кадры при панорамировании
считала простые кадры между вызовами инструмента как «медленные» — 539 из
1219 кадров оказывались дольше 16 мс просто потому, что между отдельными
вызовами `computer` проходит сетевая пауза, а `requestAnimationFrame`
исправно тикает и на простое. Рабочий метод: несколько тиков скролла в одном
`browser_batch` (без пауз между действиями внутри батча) и сравнение
**худших** кадров, а не среднего по всем.

**Измерено на живом dev-сервере, документ 1920×1080, реальным колесом мыши
(не синтетическим событием) через `computer`:**

| Фигур на холсте | Худшие кадры жеста (мс) | Устойчивое движение |
|---|---|---|
| 3 000 | 157.9 · 137.7 · 64.2 · 63.8 | ~16.5 мс/кадр |
| 10 000 | 283.1 · 277.0 · 172.2 · 128.6 · 128.0 · 125.2 · 121.2 · 107.2 | ~16.5 мс/кадр |

Вывод, а не догадка: **сам жест не заикается на всём протяжении** — как
только панорама начала двигаться, кадр стабильно укладывается в 16.5 мс
независимо от числа фигур. Дорог только **первый кадр смены направления**:
на 3 000 фигурах это 1–2 кадра дороже 60 ms, на 10 000 — уже 6–8 кадров дороже
100 мс, вплоть до 283 мс. Похоже на пересчёт стилей всего поддерева `<svg>`
при смене CSS-трансформации на общем контейнере — вложенность, а не число
кадров в движении, растёт с количеством фигур.

Порог для этапа 12 (когда решать вопрос о GPU-рендере): **если после этапов
2–9 в реальных документах регулярно оказывается 5 000+ фигур, обязательно
подтвердить, ушёл ли стартовый хитч вместе с остальными изменениями, прежде
чем откладывать GPU-рендер дальше**. Ниже 3 000 фигур текущий SVG-рендер не
создаёт заметной проблемы.

Замер `shapeAt` (линейный перебор, точка гарантированного промаха):

| Фигур | Время (fastest of 5) |
|---|---|
| 100 | ~0.008 мс |
| 1 000 | ~0.008 мс |
| 10 000 | ~0.09 мс |

На этих размерах линейный перебор пока не создаёт проблемы — числа сюда
занесены как пол для этапа 4, а не как повод его торопить.

Замер сериализации документа (`JSON.stringify`/`parse` состояния — то, что
стоит на пути автосохранения и восстановления сессии сверх постоянной
стоимости самого ввода-вывода): **~2.2 мс на 1 000 фигур**.

#### Решение: `transform` на фигуре, а не отдельная сущность-обёртка

Раздел 3.1 предполагал `VectorEntity { source, transform, geometry[],
appearance[] }` — источник и стопка модификаторов отдельно от фигуры. На
практике для этого этапа это было бы преждевременно: недеструктивные
модификаторы — это этап 9, а вводить обёртку вокруг каждой фигуры сейчас
означало бы переписать весь код, который держит `VectorShape` как плоскую
дискриминированную структуру, ради поля, которое пока нечем заполнять.

Сделано минимально необходимое для этого этапа: `transform: Matrix` добавлен
прямо в `VectorShapeBase` — то общее для всех видов фигур, что раньше было
только `rotation: number` у прямоугольника, эллипса и картинки (и отсутствовало
у пути, текста и линии — баг §2.4). Это готовит почву под `VectorEntity`
позже, не создавая сейчас двух конкурирующих представлений трансформации.

**`rotation` удалён, а не оставлен рядом.** Единственная дверь: если бы
`rotation` и `transform` существовали одновременно, они могли бы разойтись
между собой, и непонятно, чему верить при рендере. Миграция запекает старое
значение поворота в матрицу вокруг центра фигуры — числа сверены программно
(`/d/DiskD/Temp/check-rotation.mjs`), а не выведены на бумаге.

#### Как рендерится трансформация — переиспользован сам SVG

`VectorWorkspace.tsx` был плоским `state.shapes.map(renderShape)`. Стал
рекурсивным обходом дерева (`renderShapeTree`), где группа — это `<g
transform="matrix(...)">`, обёрнутый вокруг своих детей. Композицию
трансформаций всей цепочки предков делает сам браузер через вложенность
`<g>` — ни `renderShapeTree`, ни `renderShape` не перемножают матрицы
вручную. Матрицы нужны только там, где нет DOM: `shapeAt` (клик мимо фигуры
внутри повёрнутой группы должен промахнуться) и `shapeWorldBounds`
(экранная рамка выделения).

Канвас-рендер (`vector-environment.ts`, экспорт в растр) вложенности не
имеет — это плоский цикл по `state.shapes` — поэтому там трансформация
применяется явно, `context.transform(...)` с посчитанным `worldTransform`
на каждую фигуру. Раньше этот путь вообще не учитывал `rotation`; теперь он
не только компилируется, но и **правильнее**, чем был.

#### Живая проверка, с числами

Создан документ, прямоугольник и эллипс нарисованы настоящим
`left_click_drag`, выделены оба через Shift-клик по строкам панели слоёв,
сгруппированы кнопкой «Сгруппировать» — всё реальными кликами `computer`, не
вызовами API. Группа повёрнута на 30° (матрица выставлена напрямую —
готового жеста поворота фигуры в интерфейсе пока нет, это записано в
ограничениях ниже). Экранный `getBoundingClientRect()` прямоугольника:

до разгруппировки — `{x: 121.8425521850586, y: 358.8525390625, width:
114.6384506225586, height: 102.5595703125}`; после — те же четыре числа, ни
одна цифра не отличается. Это и есть «фигуры остаются там, где были»,
проверенное не рассуждением, а замером в работающем браузере.

**Ловушка метода, найденная и записанная в `CLAUDE.md`.** Клики `computer` по

#### Известные ограничения

- **Нет жеста поворота фигуры/группы в интерфейсе.** Проверка выше вращала
  группу прямой записью в `transform` через консоль — сам механизм
  трансформации проверен, ручка на холсте, за которую можно потянуть, ещё не
  сделана. У прямоугольника/эллипса/картинки раньше был `rotation`, но и у
  него никогда не было ручки — это не регресс этого этапа, а нерешённая
  задача, которая теперь хотя бы имеет на чём быть решённой.
- **Group/Ungroup в меню «Объект» не привязаны к физической клавиатуре** —
  показывают `Ctrl+G`/`Ctrl+Shift+G` как текст, как и остальные пункты этого
  меню (Duplicate, Delete и т. д.) уже делали до этого этапа. Не новая дыра,
  а тот же пробел, что был всегда в этом меню; настоящая привязка требует
  регистрации команд в каталоге (`commands/definitions`), как у растровых
  действий, и осталась за скобками этого этапа.
- **Артборды заведены как модель данных**, но создавать/двигать их через
  интерфейс негде — только флажок «Включить монтажные области» при создании
  документа, который теперь сеет один артборд размером с холст.
- **Единицы измерения (`units.ts`) и структура `Color` в ядре сделаны и
  протестированы**, но большинство числовых полей свойств (X, Y, ширина,
  радиус угла) всё ещё принимают только пиксели — подключение `parseLength`
  к каждому такому полю не входило в объём этого этапа.

#### Известные ограничения

  зуме или масштабе в цепочке предков это разное число экранных пикселей.
  Настоящее исправление требует прокинуть эффективный масштаб от вызывающей
  стороны (`VectorWorkspace`) до `shapeAt`, что шире, чем эта фигурирующая
  здесь правка габаритов/попадания.
- **У текста по-прежнему только прямоугольная область попадания**, не контур
  букв — обводка текста как таковая не хит-тестится отдельно от заливки.
  Настоящие контуры глифов — задача этапа 11 (текст через Parley/HarfRust).
- **Попадание по обводке — точное расстояние до линии**, без учёта соединений
  (`stroke-linejoin`) и торцов (`stroke-linecap`) — угол толстой обводки
  хит-тестится чуть уже, чем видно на экране. Не считается существенной
  неточностью на этом этапе.

хотя тип теперь общий для обеих сред. Переименование задело бы растровый
пакет ради вектора — вне рамок этого этапа.

**Живая проверка реальным вводом.** На dev-сервере: прямоугольник, заливка
color → gradient — на холсте появился настоящий линейный градиент
чёрный→белый (проверено через DOM: `<linearGradient
gradientUnits="objectBoundingBox">` в `<defs>`, `fill="url(#…)"` на
`<rect>`); добавлена обводка, ширина 2→8, пунктир solid→dashed, cap
butt→round, join miter→bevel — все пять значений подтверждены через
`getAttribute` на живом `<rect>` (`stroke-width="8"`,
`stroke-dasharray="16 16"`, `stroke-linecap="round"`,
`stroke-linejoin="bevel"`); режим наложения объекта normal→multiply дал
`style="mix-blend-mode: multiply"` на обёртывающем `<g>`; непрозрачность
объекта 100→50 дала `opacity="0.5"` на том же `<g>`.

Цель: появилась вторая реализация тяжёлой математики, и доказано, что она даёт

- [x] `VectorGeometryPort` в ядре (`kernel/src/vector-geometry-port.ts`):

- [x] Крейт `crates/vector-geometry`, сборка в WASM, ленивая загрузка —

      пересечение, исключение — все четыре реализованы и работают.

      с дыркой после вычитания приходит как отдельный полигон снаружи, а
      не как кольцо внутри — одно и то же упрощение с обеих сторон,
      задокументировано в `vector-geometry-port.ts`), только простые
      многоугольники на входе (кривые контуров ещё не превращаются в
      полилинии перед клиппингом — этим предстоит заняться, когда булевы
      операции реально понадобятся инструменту, не раньше)
- [x] **Один набор тестов прогоняется на обеих реализациях**
      (`apps/web/src/vector-geometry.parity.test.ts`, 21 тест: 5 фигур ×
      4 операции плюс тест на невырожденность) — сравнение не по массиву
      вершин (два разных алгоритма не обязаны отдавать точки в одном
      порядке или направлении обхода даже для одинаковой формы), а по
      плотной сетке точек «внутри/снаружи» над общим прямоугольником
      фигур, со смещением на нецелые координаты, чтобы точка никогда не
      легла ровно на общее ребро. Проверено разворотом `union` на

- [x] Замер: **~3.4–4.7× быстрее** на объединении двух 64-угольников

**Установленный на этой машине тулчейн**: `rustup` (через winget),

Цель: операции, после которых остаются кривые, а не тысяча точек.

- [x] Офсет пути (Kurbo) — `offset_path` в `crates/vector-geometry`

- [x] Преобразование обводки в контур — `stroke_to_fill`, поверх

      геометрию один раз, дальше это обычная заливка
- [x] Упрощение пути с заданной точностью — `simplify_path`, поверх
      `kurbo::simplify_bezpath`. Работает по-настоящему: почти прямая линия

      разумной точности (замерено)
- [~] Обратная аппроксимация полигонов Clipper2 в кривые — **не получилось**,
      и это не тихо забытый пункт. `simplify_bezpath` по умолчанию (и с
      подобранным вручную более широким порогом угла) сохраняет любой
      неслучайный поворот как настоящий угол — развёрнутая в полигон
      окружность неотличима от 64-угольника, который кто-то нарисовал
      специально: приблизительно 5° поворота на каждой вершине уже выше
      порога «это шум». **Замерено**: правильный 64-угольник-окружность
      остаётся на 65 командах пути при точности от 0.01 до 10 (10% от
      собственного радиуса) — упрощение не срабатывает вообще; с вручную
      расширенным порогом угла (0.2 рад) и точностью 20 — падает только до
      27 команд, не до единиц. Настоящее решение — аппроксимация методом
      наименьших квадратов через `kurbo::fit_to_bezpath` с собственной
      реализацией `ParamCurveFit` над последовательностью точек, а не
      сохраняющее-углы упрощение; это отдельная, реальная задача, отложенная
      до момента, когда булева операция понадобится инструменту в UI
- [x] Замер числа узлов после объединения двух окружностей: **цель не
      достигнута, число записано честно**. Union двух 64-угольников (радиус
      100, наложение наполовину) даёт полигон на 84 вершины; после
      `simplify_path` с точностью 1 (настройки по умолчанию, без ручного
      расширения порога угла) — **85 команд пути**, практически без
      сокращения, не «единицы». Число закреплено тестом
      (`vector-geometry.curves.test.ts`, «measured: unioning two 64-sided
      circles does NOT come back down to single-digit nodes yet») как
      честный текущий пол, а не как достижение — чтобы будущая попытка
      настоящей аппроксимации кривыми имела с чем сравниться, и чтобы этот
      пробел не мог незаметно оказаться «вроде решённым»

**Тесты**: `vector-geometry.curves.test.ts`, 8 тестов на реальном
скомпилированном `.wasm` — офсет наружу/внутрь (офсет внутрь проверен на

## 7. Ответы владельца и что из них следует

Получены 5 сентября 2026 года. Каждый ответ меняет модель, поэтому записан не
как «выбрано то-то», а вместе со следствием.

### 7.1. Артборды — по-иллюстраторски

Монтажные области **размечают холст, но не владеют объектами**. Объект может
лежать между артбордами или наполовину снаружи, и это нормальное состояние, а
не ошибка.

Следствие для модели: артборд — не узел дерева, а запись в отдельном списке
документа. Сейчас в `VectorDocumentState` стоит `artboards: boolean` — флаг
«показывать ли их вообще». Он становится `artboards: Artboard[]` с именем,
прямоугольником и настройками экспорта у каждого.

Это заметно проще фигмовских фреймов: не нужно ни обрезание по контейнеру, ни
принадлежность, ни авторазметка. Дерево документа остаётся деревом объектов.

### 7.2. Единицы — пиксели и всё остальное

Нужны px, мм, см, дюймы и пункты.

Следствие: у документа появляется разрешение (ppi) и текущая единица
отображения. **Хранение остаётся в пикселях**, перевод — в одном модуле с
тестами на каждую пару единиц.

Почему хранение в пикселях, а не в пунктах, как у Illustrator: в VRAVIO вектор
живёт бок о бок с растром и обменивается с ним ассетами, у растрового документа
разрешение уже есть, и общая единица избавляет круговой обмен от пересчёта на
каждой границе. Плата за это честная и её надо назвать: **смена ppi документа
меняет физический размер всего**, поэтому она должна быть явной операцией с
выбором — пересчитать координаты или переистолковать их, ровно как «Размер
изображения» в растре.

Поля ввода должны принимать `10мм` и `0.5in` и переводить сами.

### 7.3. CMYK нужен

Это самый дорогой из четырёх ответов, и он меняет вещь, которую позже менять
больно.

Сейчас цвет — это `fill: string | null`, то есть строка `"#rrggbb"`. Строка не
умеет быть ни CMYK, ни плашечным цветом, ни цветом с профилем. Значит цвет
становится структурой:

```
Color {
  space:      "srgb" | "cmyk" | "gray" | "lab" | "spot"
  components: number[]
  profile?:   AssetId          // ICC-профиль лежит в хранилище ассетов
  alpha:      number
}
```

И живёт эта структура **в ядре, а не в векторном пакете**, потому что растру
CMYK нужен тоже — в `docs/requirements.md` это записано отдельной строкой
(`RASTER-COLOR-002`). Один тип цвета на обе среды — это та же «единственная
дверь», что и везде: иначе появятся два несовместимых цвета и вечный перевод
между ними.

Поэтому тип цвета переезжает в **этап 2** (модель), а управление цветом целиком
— перевод по профилям, экранная цветопроба, экспорт — становится отдельным
этапом 14. Разделены они потому, что тип нужен рано и всем, а движок ICC —
большая самостоятельная работа.

### 7.4. Символы — по-иллюстраторски

Определение символа хранится в документе один раз, на холсте стоят экземпляры,
правка определения меняет все экземпляры сразу.

Следствие: экземпляр — **ссылка, а не копия**. У него своя трансформация, но
геометрия общая. Нужны «разорвать связь» (экземпляр становится обычными
объектами) и «переопределить символ». Это отдельный этап 13; при желании его
можно вытащить раньше, он зависит только от модели этапа 2.

### Этап 15. Настоящий Canvas: артборды как у Illustrator, а не как «единственная страница»

Добавлено 6 сентября 2026 по прямому разбору владельца, сравнивавшего
устройство рабочей области в Illustrator с тем, что уже в VRAVIO. Найден
реальный архитектурный пробел, не просто недоделанная функция.

**Модель данных уже правильная.** `Artboard { id, name, x, y, width,
height }`, отдельный список `VectorDocumentState.artboards: Artboard[]`,
фигуры не вложены в артборд — ровно принцип Illustrator «монтажная
область размечает холст, но не владеет объектами», зафиксированный ещё на
этапе 2 (раздел 7.1 этого документа). Один объект имеет полное право
лежать наполовину на артборде A, наполовину на B, или вообще между ними —
модель это уже допускает.

**Настоящий косяк — отсутствие самого Canvas.** У Illustrator это
отдельная, гораздо большая сущность («paperboard»/«infinite canvas» —
у Adobe ограничено физически, но на порядки больше типичного документа, с
режимом Large Canvas до ~2270×2270 дюймов), на которой артборды — просто
прямоугольники где угодно. У VRAVIO такой сущности сейчас нет вовсе:
`state.width`/`state.height` — это одновременно и «размер документа», и
жёсткая граница, за которую физически ничего не может выйти:

```
apps/web/src/VectorWorkspace.tsx:421
<svg width={state.width} height={state.height} viewBox="0 0 {state.width} {state.height}">
```

Второй артборд с `x: 2000` в `artboards[]` окажется вне `viewBox` —
невидим и недостижим указателем, а не «объект вне активного артборда, но
на canvas», как должно быть. Сейчас документ VRAVIO ведёт себя как один
артборд Illustrator, а не как его canvas. Из этого пробела прямо
вытекают все недостающие куски ниже — они не сделаны не потому что
забыты, а потому что для них физически нет фундамента.

- [ ] Развязать «размер документа для экспорта по умолчанию» и «границы,
      за которые ничего не может выйти» — настоящий больший canvas (не
      обязательно буквально бесконечный; заметно больше типичного
      документа с паном за пределы текущего видимого прямоугольника),
      артборды — прямоугольники на нём
- [ ] `activeArtboardId` на документе; активный артборд обозначен отдельной
      рамкой, на него ссылаются команды вида «уместить артборд в окне»,
      «вставить на место», привязанные к артборду линейки/экспорт
- [ ] Artboard Tool: создание, перемещение, изменение размера, переименование,
      X/Y/W/H, preset, ориентация — тот же уровень, что у остальных
      инструментов панели (`Shift+O` у Illustrator)
- [ ] Панель Artboards: список, дублирование, удаление, «уместить в
      артворк» — параллельно панели слоёв, не вместо неё
- [ ] `Move Artwork with Artboard` — переключатель на операции
      перемещения артборда: без него артборд уходит, объекты остаются;
      с ним — находит артворк, пространственно пересекающийся с
      прямоугольником артборда, и двигает вместе. Это операция
      инструмента (`artworkIntersectingArtboard(artboard)` в момент
      перетаскивания), не постоянное владение через `object.artboardId`
- [ ] Reorder (логический порядок в панели — список артбордов, не их
      расположение) отдельно от Rearrange (Grid by Row/Column — физическая
      перестановка прямоугольников на canvas с заданием spacing/строк/
      столбцов/направления, опционально с `Move Artwork with Artboard`)
- [ ] Порядок наложения объектов остаётся делом Layers/stacking order —
      артборды по-прежнему не участвуют в z-порядке фигур, даже когда их
      прямоугольники на canvas перекрываются
- [ ] Локальная система координат артборда: `rulerOrigin`, режим линеек
      Global/Artboard (переключение начала отсчёта `(0,0)` в зависимости
      от активного артборда — по умолчанию его левый верхний угол)
- [ ] `Guide { scope: "global" | "artboard"; artboardId?: string }` —
      направляющая, ограниченная конкретным артбордом, отдельно от
      сквозной через весь canvas (зависит от этапа 5's ruler-guides,
      которых у вектора пока тоже нет — см. этап 5's собственную честную
      дыру)
- [ ] Bleed как ещё один уровень наружу артборда (Top/Bottom/Left/Right в
      настройках документа), применяется вокруг каждого артборда, а не
      один раз на весь canvas
- [ ] Экспорт по конкретному артборду (crop boundary = его прямоугольник),
      а не по `state.width`/`state.height` документа целиком — несколько
      артбордов экспортируются по отдельности в PNG/JPEG/SVG/PDF и т. п.
- [ ] Проверка, ради которой всё затевалось: два артборда на разных концах
      canvas, третий объект физически между ними — все три остаются
      полноценными, редактируемыми объектами одного дерева; выключенный
      `Move Artwork with Artboard` двигает пустой прямоугольник, не трогая
      артворк; включённый — тянет за собой ровно то, что пространственно
      пересекается с артбордом на момент начала перетаскивания

## 9. Долг: инструмент «Перо» — обзор возможностей и жестов

Добавлено 6 сентября 2026 года по внешнему обзору (владелец переслал разбор
от стороннего ассистента). Математическая основа пера уже в порядке —
настоящий кубический Безье, `handleIn`/`handleOut` с зеркалированием, весь
нарисованный контур попадает в историю одной операцией. Не хватает жестов и
интеграции с уже существующей инфраструктурой (снаппинг, Node Tool), а не
модели данных. Донор жестов — **Krita** (Bezier Curve Tool) и **Inkscape**
(pen-tool.cpp/node-tool.cpp), оба под GPL: см. раздел 4 — перечень
возможностей, не код.

Первый приоритет (без этого перо не ощущается профессиональным инструментом):

- [ ] Замыкание контура кликом по первой точке, а не только через ПКМ →
      Close Path — `closePath()` в `pen.tsx` уже полностью готов, не хватает
      только жеста/hit-теста по первой точке курсором
- [ ] Резиновая линия (rubber-band preview) следующего сегмента между
      последней точкой и курсором в `Overlay` пера — сейчас пусто
- [ ] `Shift` во время клика/протяжки ручки — фиксация угла сегмента и ручки
      кратно 45° (`ToolPointer` уже несёт модификатор, `pen.tsx` его не
      читает)
- [ ] `Alt` во время протяжки новой точки — сразу оторвать `handleOut` от
      `handleIn`, независимый corner point (Node Tool это уже умеет для
      существующих точек — перо должно уметь то же самое в момент создания)
- [ ] Снаппинг — `context.snapping` уже передаётся каждому инструменту
      (этап 5), но `pen.tsx` его не использует вообще; перо должно
      привязываться минимум к узлам, сегментам, габаритам и сетке, как и
      остальные инструменты

Второй приоритет:

- [ ] Временный Node Tool через `Ctrl`/`Cmd`, зажатый во время рисования
      пером — Node Tool уже содержит нужную логику перетаскивания точек и
      ручек, пера не хватает только временной передачи жеста
- [ ] Добавление узла кликом по существующему сегменту, удаление — кликом
      по существующему узлу, без выхода из инструмента «Перо»
- [ ] Состояния курсора (обычный / +добавить / −удалить / ○замкнуть /
      ↗продолжить), чтобы результат клика был предсказуем до самого клика
- [ ] Продолжение существующего открытого контура кликом по его концу, и
      соединение двух открытых контуров — сейчас каждый жест пера всегда
      создаёт новый `path` через `createShape()`

Третий приоритет, после первых двух:

- [ ] Умное преобразование угловой/сглаженной точки, автосглаживание
- [ ] Точный числовой ввод координаты при размещении точки
- [ ] Удаление узла с сохранением кривизны контура (не просто прямая между
      соседями)

Найдено и требует отдельной проверки, не только жест: `pen.tsx` берёт цвет
из `context.foregroundColor`, а не из `context.options.color` — при этом
`strokeWidth` действительно читает `context.options`. Если поле «Цвет» в
панели параметров инструмента не синхронизировано отдельно с глобальным
foreground-цветом, `vector.pen`'s `Color`-опция — мёртвый чекбоксом
(правило 3 `CLAUDE.md`), который стоит подтвердить и исправить до начала
работы над остальным списком.

Отдельно стоит перепроверить обработку двойного клика: сейчас
`pointerDown` сначала всегда добавляет новую точку и только потом проверяет
`detail >= 2` для завершения контура — есть риск, что второй клик двойного
клика успевает добавить точку почти в той же позиции перед завершением,
оставляя вырожденный нулевой последний сегмент.
- [ ] Сверка с эталонными плашками, а не «на глаз»
