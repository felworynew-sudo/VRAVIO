# ТЗ: переход на каталожную структуру

Документ описывает переход VRAVIO от «архитектуры в компоненте» к каталожной,
при которой добавление инструмента, окна, команды, правила или плагина — это
**новый файл в известном каталоге**, а не правка существующего кода.

Язык документа — русский, идентификаторы и имена файлов — английские, как во
всём репозитории.

**Как пользоваться.** Каждый этап заканчивается состоянием, в котором проект
собирается, проходит тесты и работает. Между этапами можно остановиться на
любой срок. Отмечайте выполненное прямо здесь: `- [x]`. Строка считается
закрытой, только когда есть и реализация, и автопроверка — то же правило, что в
`docs/requirements.md`.

**Чего этот документ не делает.** Он не меняет поведение редактора. Ни один
этап не должен менять то, что видит пользователь, кроме явно оговорённых
(панель инструментов с `(...)`, окно загрузки). Всё остальное — перекладка.

**Главное.** Поведение инструментов не в файлах инструментов. В

|---|---|

| `raster.move` | 1076, 1304–1310, 1326, 1944 |
| `raster.burn` | 801, 1247, 1356, 1661, 1735 |

**Остальное:**

- `tools.ts` — 30 инструментов одним массивом в одном файле; описание

- `commands.ts` — 294 строки одним файлом, без разделения по средам.

- Нет: плагинов, сценариев, кистей, паттернов, JSON темы, движка правил,
  бэкапов с выбором места, десктоп-сборки.

## 2. Границы дисциплины

Самое важное решение всего перехода. Атомарный дизайн применяется **не ко
всему**, иначе производительность упадёт.

| слой | дисциплина | почему |
|---|---|---|
| Интерфейс: поля, ползунки, окна | Атомарный дизайн: атом → молекула → организм | Переиспользование и предсказуемость важнее микросекунд |
| Каталоги: инструменты, окна, команды, правила, плагины | Декларативные данные + реестр по glob | Расширение файлом, а не правкой |
| Движок: пиксели, композит, тайлы, маски | Data-oriented: плоские типизированные массивы, батч-операции | Вызов на пиксель при 2 Мп/кадр дороже всей полезной работы |

**Атомарность движка — это атомарность операций, а не вызовов.** Одна операция
= один файл, экспортирующий функцию над целым буфером. Внутри неё цикл остаётся
плотным, без обратных вызовов и без диспетчеризации по строке.

Все выигрыши, достигнутые проектом, получены снятием абстракции в горячем
пути — компоновкой по тайлам вместо целого холста, хранением слоя в его
собственных границах вместо размера канваса, блочным копированием вместо
двух проходов композита при перемещении, перезаписью только изменившегося
буфера при автосохранении. Переход не имеет права вернуть ни один из этих
приёмов.

**Цифры перепроверены этапом 0** (раздел 5, этап 0) на бенчмарке
`packages/env-raster/src/performance.bench.test.ts` и
`packages/kernel/src/performance.bench.test.ts`, а не взяты по памяти из
более ранней работы, как было при первой редакции этого документа — тогда
композит оценивался в ~14 мс, перемер на реалистичной фикстуре (21 слой,
1920×1080, слои размером с типичный мазок, а не во весь холст) дал ~27 мс.
Расхождение не опровергает саму оптимизацию: композит документа с 46
слоями во весь холст без тайлов стоит 428 мс, с тайлами — 38 мс (это
задокументировано прямо в коде, `render.ts`, комментарий у
`subdivideAbove`) — четырёхкратный запас у порога бенчмарка (×6 от
измеренного) рассчитан от актуального числа, а не от цифры, которая не
подтвердилась.

## 4. Контракты

Контракт — это то, что позволяет реестру подхватить файл. Каждый описан ниже с
обоснованием полей.

### 4.1 Инструмент

Во всех контрактах ниже `label: LocalizedText` — тип из
`apps/web/src/i18n.ts`, добавленный на этапе 1: `{ en: string; ru?: string;
uk?: string; es?: string; de?: string; ja?: string; zh?: string }`, `en`
обязателен, остальные падают на английский через `resolveLabel`.

Набор хуков **выведен из кода**, а не придуман: это те функции, в которых
сегодня стоят 49 ветвлений, с числом ветвлений в каждой.

| сегодняшняя функция | ветвлений | хук контракта |
|---|---|---|
| `handlePointerDown` | 30 | `onPointerDown` |
| `appendBrushPoint` | 6 | `onStrokePoint` |
| `finishGesture` | 5 | `onGestureEnd` |
| `onDropModel` | 3 | `onDrop` |
| `handleWheel` | 2 | `onWheel` |
| `updateBrushCursor` | 1 | `cursor` |
| `beginNavigation` | 1 | `onNavigationStart` |
| `handlePointerMove` | 1 | `onPointerMove` |

```ts
export interface ToolDefinition {
  id: string;                       // "raster.brush"
  order: number;                    // положение в панели по умолчанию
  group?: string;                   // общая ячейка панели и общая буква
  label: LocalizedText;
  icon: string;                     // имя файла в icons/
  shortcut?: string;

  options: readonly ToolOption[];   // как сейчас — панель строится сама

  /** Типы слоёв, на которых инструмент работает. Заменяет RASTER_ONLY_TOOLS. */
  appliesTo: readonly RasterLayerKind[];
  /** Что делает с документом. Читается движком правил. */
  touches: "pixels" | "selection" | "view" | "vector" | "none";
  /** Требует растеризации нерастрового слоя перед работой. */
  requiresRasterized?: boolean;

  /** Прицелы. Первый — по умолчанию; переключение по контексту или клавише. */
  cursors: readonly CursorRef[];

  /** Окно тонкой настройки, если ползунков на панели мало. */
  settingsModal?: string;           // id из modals/
  contextMenu?: readonly string[];  // id команд для правого клика по холсту

  onPointerDown?(ctx: ToolContext, event: ToolPointerEvent): void;
  onPointerMove?(ctx: ToolContext, event: ToolPointerEvent): void;
  onStrokePoint?(ctx: ToolContext, point: StrokePoint): void;
  onGestureEnd?(ctx: ToolContext): void | Promise<void>;
  onWheel?(ctx: ToolContext, event: ToolWheelEvent): boolean;
  onNavigationStart?(ctx: ToolContext, event: ToolPointerEvent): boolean;
  onDrop?(ctx: ToolContext, files: readonly File[]): void | Promise<void>;
  onKey?(ctx: ToolContext, event: KeyboardEvent): boolean;
  onDeactivate?(ctx: ToolContext): void;   // обязателен, если есть состояние
}
```

`ToolContext` — единственная дверь инструмента наружу. Он **не даёт** прямого
доступа к React-состоянию: только документ, вьюпорт, настройки, выделение и
метод фиксации правки. Это и есть то, что делает правило невозможным обойти.

```ts
export interface ToolContext {
  readonly document: RasterDocumentState;
  readonly viewport: Viewport;
  readonly options: Record<string, unknown>;   // настройки этого инструмента
  readonly selection: PixelSelection | null;
  readonly activeLayer: RasterLayer | null;
  /** Единственный путь к пикселям. Проводит правку через движок правил. */
  commit(edit: PixelEdit): Promise<void>;
  /** Всё, что рисуется поверх холста, — только отсюда. */
  overlay: OverlayHandle;
  run(commandId: string, args?: unknown): Promise<void>;
}
```

### 4.3 Команда

Контракт ядра уже есть. Добавляются три поля — **все три нужны для сценариев**:

```ts
export interface CommandDefinition extends Command {
  /** Куда софт вставляет пункт: меню, контекстное меню слоя, панель, палитра. */
  surfaces: readonly ("menu" | "palette" | "layer-context" | "canvas-context" | "toolbar")[];
  /** Аргументы. Без схемы сценарий нечего записывать и нечем воспроизводить. */
  args?: ArgSchema;
  /** Запрещена к записи в сценарий (сама запись, воспроизведение, undo). */
  neverRecord?: boolean;
}
```

Отмена не отдельное поле: команда обязана выполняться через
`history.execute()` и потому обратима по построению. Команда, которая правит
документ мимо истории, — ошибка, и её ловит контрактный тест (см. 6.3).

### 4.4 Правило

```ts
export interface RuleDefinition {
  id: string;
  order: number;               // порядок применения детерминирован
  applies(edit: PixelEdit, ctx: RuleContext): boolean;
  /** Преобразует правку. Вето — вернуть null. */
  transform(edit: PixelEdit, ctx: RuleContext): PixelEdit | null;
}
```

Первые правила, которые переезжают сюда из разных мест кода:

1. `selection-confines-edits` — из `confineToSelection`
2. `lock-transparent-pixels` — из `paintMask`
3. `lock-pixels` / `lock-position` — сегодня разбросано
4. `layer-kind-guard` — из `RASTER_ONLY_TOOLS`
5. `clipping-mask-bounds`

**Урок, который надо закрепить.** Точка-предохранитель для выделения
существовала, но одна строка (`commitRevision`) дотянулась мимо неё к
необрезанному буферу: экран показывал обрезанное, а redo вернул бы полное.
Починено коммитом `b7c1f84`. Вывод для движка правил: недостаточно иметь
единственное место проверки — до **всех** потребителей (экран, история,
хранилище, экспорт) должен доходить **один и тот же объект**. Это проверяемое
свойство, и на него нужен тест.

### 4.5 Элемент интерфейса

Атомы — с полным поведением, а не «просто input».

- **`NumberBox`** — ввод цифрами; стрелки ↑↓; колесо мыши; перетаскивание вверх-вниз
  с зажатой ЛКМ; `Shift` — крупный шаг, `Alt` — мелкий; принимает единицы
  (`1 см`, `1 px`, `1 пикс`, `10%`) и приводит их по текущим настройкам
  документа; `Esc` — откат к значению до правки.
- **`Slider`** — почти всегда в паре с `NumberBox`, двусторонняя связь; `Alt` —
  точный режим; двойной клик — значение по умолчанию.
- **`Curve`** — интерактивная, точки добавляются/удаляются/тащатся,
  используется коррекциями и Camera Raw.
- **`Histogram`** — интерактивная там, где задаёт уровни.
- **`EyedropperButton`** — временно включает инструмент пипетки и возвращает
  цвет **в вызвавшее окно**, после чего восстанавливает прежний инструмент.
- **`ValueBadge`** — плашка с числом у курсора (размеры при трансформации);
  единица измерения берётся из настроек, а не зашита.

Правило для всех оверлеев: **интерфейс не масштабируется зумом**. Размеры — в
экранных пикселях. Единственное исключение — след инструмента (кольцо кисти),
потому что он показывает реальный отпечаток. Проверяется тестом.

## 5. Этапы

Каждый заканчивается зелёными тестами и работающим приложением.

### Этап 0. Замки

Перекладка без страховки — это разрушение. Сначала страховка.

- [x] Бенчмарк композита, перемещения, обрезки правки по границам и памяти
      слоёв — `packages/env-raster/src/performance.bench.test.ts`;
      автосохранения — `packages/kernel/src/performance.bench.test.ts`.
      Цифры перемерены на текущем коде, а не взяты из памяти:

      | операция | старая цифра (из памяти) | перемерено сейчас | как задан порог |
      |---|---|---|---|
      | композит 21 слоя 1920×1080 | ~14 мс | **~27 мс** | ×6 от измеренного |
      | перемещение слоя (block-copy) | ~14 мс/кадр | **~0.7 мс** | абсолютный пол 5 мс |
      | обрезка правки по границам | — | **~8 мс** | ×6 от измеренного |
      | автосохранение (1 из 21 буфера) | ~8 мс | **<1 мс** | абсолютный пол 5 мс |
      | память пикселей, 21 слой | ~3.1 МБ | **~13.4 МБ** на этой фикстуре | <30% от «все слои в размер холста» |

      Старая цифра композита (14 мс) не подтвердилась — либо была измерена на
      документе с более компактными слоями, либо ошибочно перенесена из
      контекста предыдущей сессии. **CLAUDE.md и раздел 2 этого документа
      обновлены**: 14 мс убрано как факт, оставлено только со ссылкой на то,
      что оно непроверенное.

      Первая версия фикстуры сама была неправильной: все 21 слой на весь
      холст непрозрачным цветом с дробной прозрачностью — это заставляет
      каждый пиксель идти по самой медленной ветке блендинга на каждом слое
      сразу, и дало бессмысленные ~500 мс. Слои по всему холсту вообще
      противоречат сути самой оптимизации (166→3.1 МБ достигнуты именно
      потому, что реальные слои не занимают весь холст). Исправлено:
      единственный фон на весь холст + 20 слоёв реального размера мазка,
      проведённых через `setLayerPixels`/`trimToContent`, как это делает
      настоящая правка.

      Порог памяти получил аналогичную правку: первая версия требовала
      «меньше 10 МБ» — число, придуманное не глядя на то, что один фоновый
      слой на 1920×1080 уже весит 8.3 МБ. Заменено на структурное сравнение

#### Навигация: второй контракт, а не натянутый первый

Отложено это было правильно. Разбор показал, что натянуть навигацию на
`RasterToolDefinition` нельзя, и вот почему: `hand`/`zoom`/`rotateView`
живут на **другом элементе** (мастерская, не холст), в **фазе перехвата**
(иначе жест до них не дойдёт) и в **клиентских** координатах (сдвиг на
сорок экранных пикселей остаётся сорока пикселями при любом зуме, а
перевод в документные и обратно только терял бы точность). Тащить их через
мост холста означало бы сломать перетаскивание по серому полю вокруг
холста — там обработчики холста не срабатывают вовсе, а панорамировать
оттуда надо.

Поэтому у каталога появился второй набор хуков — `NavigationHooks` рядом с
`RasterToolDefinition`, в том же файле определения. Инструмент несёт либо
одни, либо другие, и контрактный тест эту границу держит: инструмент с
обоими наборами имел бы половину поведения мёртвой, потому что до
пиксельных хуков жест просто не доходит.

Что осталось у хоста — всё, что **не** активный инструмент: пробел и
средняя кнопка как временная рука, пробел с модификатором как временный
зум, колесо, «вписать в окно». Это не выбор инструмента, это перекрытие
любого выбранного. Работают они через те же хуки, так что «пробел — это
временная рука» не имитация руки, а буквально она.

Контрактный тест поймал перенос сразу и по делу: он гонял новые
инструменты через хуки холста, которых у них нет, — все проверки проходили
впустую, а «настройка ничего не меняет» упала. Теперь у навигационных
инструментов свой прогон: жест собирается и подаётся в `begin`/`move`/`end`
с записывающим контекстом, договор `"done"` соблюдается так же, как его
соблюдает хост. Три новые проверки — «двигает вид и ничего больше», «вообще
что-то делает», «каждая настройка меняет результат» — проверены на
невакуумность по отдельности.

Живая проверка настоящим вводом: рука панорамирует ровно один к одному
(85,53 CSS-пикселя на перетаскивание в 85,53); зум перетаскиванием даёт
`exp(dx·0.01)` с точностью 0.1%; щелчок без перетаскивания — ровно ×1.25;
настройка «масштабирование перетаскиванием» действительно меняет поведение
(то же перетаскивание даёт ×1.25 вместо ×3.56); вращение — 0.3° на пиксель;
пробел при активном «вращении вида» панорамирует и **не** трогает угол;
колесо панорамирует; кисть по-прежнему получает свой жест и рисует по
повёрнутому на 57.6° холсту.

**Две вещи проверить настоящим вводом не удалось, и это ограничение
автоматизации, а не порта.** Браузерная автоматизация не доставляет
`shiftKey` в события указателя (проверено отдельно: во всех событиях
перетаскивания `shiftKey: false`), поэтому привязка вращения к 15° осталась
непроверенной вживую; и средней кнопки мыши в перетаскивании у неё нет.
Обе ветки кода не менялись при переносе — читают тот же `event.shiftKey` и
`event.button === 1`, что и до него.

#### `magicWand` и `marquee`/`ellipseMarquee`/`lasso` — выделение как второй писатель

`raster.fill` научил контракт писать пиксели. Четыре инструмента выделения
научили его писать `state.selection` — другой вид записи, с другой ценой и

**`magicWand`** оказался таким же простым, как заливка: одна изолированная
ветвь, один клик, перенос прошёл контракт с первого раза (25/25).

**`marquee`/`ellipseMarquee`/`lasso`** в коде — не три ветви, а один общий
конечный автомат (`selectionGesture`) на три id, различаемых полем `kind`.
Та же причина, по которой семья кистей ждёт своей сессии: общий код нельзя
перенести по частям, не задвоив его. Но в отличие от кистевого пайплайна,
здесь общая часть небольшая и чистая — сделано одной реализацией
(`marquee-selection.tsx`, функция `createMarqueeTool(id, kind)`) и тремя
файлами-инструментами в один экран кода каждый, вызывающими её со своим id
и формой.

**Контракт получил `commitSelection`** — отдельный от `commit` метод, не
перегрузка: выделение стоит на два порядка дешевле пиксельного буфера (байт
на пиксель, без ревизии ассета), так что тащить через него всю машинерию
`commitPixels` было бы неверно по устройству, не только по имени.

**И `spaceHeld: boolean`** — не модификатор указателя, а состояние клавиши
пробел, которое может измениться посреди жеста независимо от событий
указателя. Ровно это и держит нажатие пробела: `marquee`/`ellipse`/`lasso`
разрешают сдвинуть уже рисуемую область пробелом, не отменяя выделение —
поведение было и раньше, дропать его при переносе значило бы тихий откат
уже сделанной по твоей прямой просьбе работы («и я должен иметь возможность
перетаскивать область выделенную»).

**Сохранено и перетаскивание уже существующего выделения** (клик внутри
выделенной области двигает её, не пиксели — Move-инструмент отвечает за
пиксели). Живой предпросмотр во время перетаскивания раньше был отдельным
состоянием компонента (`marqueePreview`), которое хост писал сам; теперь

не переизобретая их отрисовку в самом инструменте.

**Пришлось сохранить кусок старого пути.** У `raster.patch` есть резервный
сценарий: если выделения ещё нет, он сам рисует лассо перед тем как

#### `raster.fill` — что перенос потребовал от контракта

Контракт этапа 3 знал только про чтение (пипетка). Заливка — первый
писатель, и понадобилось реально новое:

- **`paintTarget: { kind: "pixels" | "mask"; layerId }`** — куда идёт
  рисование: в пиксели слоя или в маску, которую слой сейчас редактирует.
  Резолвится хостом один раз за рендер, потому что зависит от состояния
  оболочки («какой слой сейчас в режиме редактирования маски»), а не от
  инструмента.
- **`paintColor: string`** — уже учитывает режим маски (чёрный/белый вместо
  цвета переднего плана).
- **`paintMask: Uint8ClampedArray | undefined`** — единая маска выделения +
  «закрепить прозрачность», та же, что раньше называлась `brushMask` в
  компоненте. `undefined` — не частный случай, а быстрый путь «ничего не
  ограничивает»; материализовывать полную маску только ради типа значило бы
  вернуть цену, которую уже когда-то убрали.
- **`targetPixels()`** — текущее содержимое цели рисования (пиксели слоя
  или маска-как-RGBA), в отличие от `layerPixels()`, которое всегда о самом
  слое независимо от режима редактирования.
- **`commit`** получил необязательные `target`/`layerId`, по умолчанию —
  `paintTarget`. Инструмент, пишущий в другой слой (как автовыбор при
  перемещении), назовёт его явно.

Ничего из этого не выдумано заранее: каждое поле — то, что старая ветвь
`raster.fill` в `RasterWorkspace.tsx` реально читала.

#### Дефекты, найденные контрактным тестом на живом пишущем инструменте

Тест из этапа 4 был проверен на пипетке (которая не пишет) и на нарочно
испорченных игрушечных инструментах — но не на настоящем писателе. Заливка
им стала, и тест поймал три вещи, ни одна из которых не была багом
инструмента:

1. **Опция `color` — не то, чем кажется.** Проверка «опция должна влиять на
   результат» варьировала `context.options.color`, но заливка (как и вся
   семья кистей) красит через `context.paintColor`, а не через свою опцию
   `color`. Оказалось, это осознанный дизайн: `App.tsx`'s `OptionsBar`
   всегда подставляет в `color`-поле `effectiveForegroundColor` и пишет
   изменение через `setForegroundColor`, а не в `toolOptions` — цветовой
   свотч на панели инструмента это просто зеркало глобального переднего
   плана. Тест правил не инструмент — добавлена отдельная проверка,
   варьирующая `paintColor` напрямую, для любого инструмента с опцией типа
   `color`.
2. **Сигнатура результата видела только подписи коммитов, не содержимое.**
   Заливка коммитит с одной и той же подписью независимо от допуска —
   меняются только сами пиксели. Проверка «опция влияет на результат»
   сравнивала подписи и не видела разницы. Исправлено: сигнатура включает
   содержимое `after`.
3. **Фикстура документа была слишком однородной для допуска.** Заливка от
   затравочной точки сравнивает каждый пиксель ровно с цветом затравки —
   плоская заливка без вариации красится одинаково при любом допуске, потому
   что сравнивать не с чем. Перекрашено по расстоянию от точки нажатия
   (`|x-10|+|y-10|`), детерминированно и предсказуемо, вместо случайного
   узора, в котором нельзя было заранее сказать, что допуск вообще на что-то
   повлияет.

**Найден и закрыт настоящий пробел покрытия**, не связанный с заливкой
напрямую. Правило «инструмент не может обойти выделение» проверялось только
утверждением («заливка мимо `commit` невозможна, потому что `commit` — это
`commitPixels`») — само по себе верно, но ничего не *исполняющая* проверка.
Добавлен тест: рисование со всюду-нулевой `paintMask` не должно менять ни
одного пикселя. Подтверждено, что он ловит нарушение — заливка, вручную
заставленная передавать `undefined` вместо `context.paintMask`, красит весь
холст, тест падает с точным указанием, что и где изменилось.

**Проверено вживую**, с реальными пиксельными числами, а не только тестами:
клик красит холст; отмена возвращает исходный синий (`R:255→51`); повтор
возвращает красный; прямоугольное выделение на левую треть — заливка

#### `brush`/`pencil`/`highlighter`/`eraser` — общий мазок и живой предпросмотр мимо React

Отложенная с начала этапа 5 связка (см. «Второй кандидат по порядку» выше).
В коде `RasterWorkspace.tsx` это был один пайплайн на семь инструментов
(четыре кистевых плюс `blur`/`smudge`/`dodge`/`burn`), так что перенос начат
с разбора, что из семи веток общее, а что — тональные инструменты, которые
остаются в старом коде. Общее: слежение за жестом, квадратичное сглаживание
кривой, коалесцированные события указателя, `Shift`-клик рисует прямую
линию, `Alt`-клик сэмплирует цвет. Частное — ровно два флага: стирает ли
мазок (`eraser`) и прижата ли жёсткость к 1 (`pencil`). `highlighter` не
третий случай, а `brush` с другим значением опции по умолчанию в `tools.ts`
— в логике инструмента разницы нет. Реализовано одной фабрикой
(`paint-stroke.ts`, `createPaintStrokeTool(config)`) и четырьмя
файлами-инструментами в один экран кода, как раньше `marquee-selection.tsx`.

**Контракт получил три новых члена**, все — потому что реальный мазок,
драгающийся по холсту, потребовал их, не заранее:

- **`schedulePreview(pixels, target, layerId, dirty?)`** — рисует
  промежуточный результат прямо в канвас, мимо React. Перетаскиваемый мазок
  может дать сотни `pointermove` в секунду; прогонять каждый через
  `setState` значило бы откатить оптимизацию RASTER-PAINT-002 (компоновка
  428 мс → 14 мс за счёт ухода из цикла рендера React, `CLAUDE.md` §5).
  Вызовы схлопываются в одну перерисовку на кадр (`requestAnimationFrame`),
  переиспользуя существующие `renderWorking`/`renderWorkingRegion` моста, а
  не изобретая новый путь отрисовки. `dirty` — тот же обрезанный по региону
  путь, что уже был у `scheduleWorkingRender`.
- **`commit` получил необязательный `bounds`** — тот же dirty-регион для
  тайлового кеша, который раньше терял только что перенесённые `fill` и
  `magicWand` (для них это было не важно: заливка и клик волшебной палочки
  меняют весь холст или единичный клик, не растянутый мазок). Без него
  каждый коммит мазка форсировал полную перекомпоновку холста независимо от
  того, насколько маленьким был штрих — именно то, от чего избавлялись
  тайлы (`CLAUDE.md` §5, 428 → 38 мс).
- **`lastStrokePoint`/`setLastStrokePoint`** и **`setMaskForegroundWhite`** —
  оба читают/пишут состояние, которое живёт на хосте, а не в состоянии
  инструмента: `lastBrushPointRef` должен пережить не только жест
  (отпустили — нажали снова с `Shift` в другом месте), но и переключение
  между разными инструментами связки и обратно — то, что `onDeactivate`
  обнулил бы, будь это состояние инструмента. `setMaskForegroundWhite`
  нужен для `Alt`-сэмплирования на маске: там результат не hex-цвет, а то,
  по какую сторону порога чёрное/белое лежит уже засэмплированный пиксель.

функция без React, ровно то место, которому её отдаёт `CLAUDE.md` §5.

**`Alt`-сэмплирование цвета внутри `onPointerDown` кисти**, не в мосте —

хосте, оно бы никогда не сработало для кистевых id. Прочитан ровно тот же
порядок, что был в старом коде: `Alt` проверяется до `layer.locked` (сэмпл
— не правка, блокировка слоя ему не мешает), но после гейта
`requiresRasterized` — то есть `Alt`-клик на текстовом/корректирующем слое
всё ещё сначала предложит растеризацию, а не просто прочитает цвет; это
не новый пробел, а то же самое поведение, что было у семи инструментов в
старом коде (гейт `RASTER_ONLY_TOOLS` тоже стоял раньше `Alt`-проверки).

**Убран действительно мёртвый код.** Раз кистевые id больше никогда не

последний сегмент мазка (`else if (activeToolId !== blur/smudge/dodge/burn)`)

своим явным веткам, а `blur`/`smudge`/`dodge`/`burn` явно исключены
условием. Удалена вместе с мёртвыми ветвями ярлыка коммита
(`eraser`/`pencil`/`highlighter`). Оставлено нетронутым — сознательно —
почти симметричное место в `appendBrushPoint`: та же по виду ветка там
всё ещё исполняется для `raster.patch`, который использует общий путь
мазка для промежуточного предпросмотра при перетаскивании (сама заплатка
считается один раз, при отпускании). Внешне похожий мёртвый код в двух
местах — но мёртвый только в одном; вычищено только там, где действительно
мёртв.

**Дизайн-решение, а не перенос один в один: `onDeactivate` коммитит
незавершённый мазок.** У старого императивного кода не было ответа на
«переключили инструмент, не отпустив кнопку» — `gesture.current` просто
переставал совпадать с `activeToolId`, и остаток мазка красился уже
настройками нового инструмента в тот же буфер. Контракта такого случая
не было вовсе. Выбрано: `onDeactivate` коммитит то, что уже нарисовано,
вместо того чтобы бросить буфер или перекрасить его чужим инструментом —
строго лучше старого поведения, не только другое.

одним лишним вызовом `drawQuadraticStrokeSegment(curveStart, pending,

равной конечной, что вырождает кривую почти в прямую до неё. Перенесено
дословно в `onGestureEnd`.

поведение бит в бит для любого вызова, который его не передаёт (существующие

«интервал между дабами» для него не существует архитектурно. Убрал

прямоугольника), а какая это фигура выбирается в панели опций, а не в
состоянии перетаскивания.

**`text`** оказался другим по существу, не по объёму: набор текста, курсор,
выделение символов — целиком браузерный `<textarea>`, ничего из этого не
переписывается. Часть, которую переносил контракт
(`onPointerDown`/`onPointerMove`/`onGestureEnd`) — это только тест по
существующим текстовым слоям и математика перетаскивания рамки/кривой,
самодостаточный кусок в духе `marquee-selection.tsx`. Настоящая новизна —
`Overlay`, которому впервые понадобилось не рисовать фигуру по состоянию, а
самому вызывать `setState`/`commitDocument`, пока пользователь печатает.
Контракт получил `context` третьим пропсом `Overlay` (в дополнение к уже
бывшим `state`/`document`/`options`) — тот же объект, что получает любой
хук.

**Ещё две новые точки контракта, обе — под то, что уже делал старый код,
не выдуманные заранее:**
- **`ctx.previewWithLayerHidden(layerId | null)`** — живое редактирование
  показывается HTML-оверлеем, а не растровыми пикселями; если не убрать
  собственные растровые пиксели слоя из-под текстареи, текст покажется
  дважды. Старый код делал это прямым `putPixels(canvas, ...)` в обход
  React; метод — то же самое, названное и оформленное как часть контракта.
- **`ctx.setActiveLayer`** и **`ctx.foregroundColor`** — выбор существующего
  текстового слоя кликом не должен создавать шаг истории (в отличие от
  `commitDocument`), а цвет текста должен быть настоящим цветом переднего
  плана, а не `paintColor`, который подменяется на чёрный/белый, пока где-то
  редактируется чужая маска слоя, — старый код читал `foregroundColor`
  напрямую именно поэтому.

**Найденная и решённая ловушка: снятие фокуса при размонтировании.**
Escape и Ctrl/Cmd+Enter оба сами очищают `draft` (значит, размонтируют
текстареу) — а снятие DOM-узла с фокуса синхронно стреляет собственным
`blur`, который без защиты запустил бы `onBlur`'s коммит ещё раз поверх
уже отменённого/закоммиченного черновика. Старый код держал именно для
этого `textCancelRef`; перенесено тем же приёмом, только `useRef` внутри
`Overlay`-компонента (`suppressBlurRef`), а не модульным рефом хоста —
между инструментом и его собственным оверлеем ничего общего не остаётся,
кроме `TState`.

**Дизайн-решение, а не перенос один в один.** В старом коде текстареа
рисовалась по одному `textDraft`, вообще не глядя на `activeToolId` — можно
было набирать текст, переключившись на другой инструмент, и он оставался
открытым. У каталога `Overlay` рендерится, только пока сам инструмент
активен: переключение убрало бы недописанный текст молча. `onDeactivate`
коммитит незавершённый черновик — тот же выбор, что уже был у кисти
(«сохранить работу лучше, чем потерять»), не то поведение, что было, а то,
что должно быть.

**Тихо исправленный, не переизобретённый баг.** Пустой коммит по
существующему слою (`commitText`'s ранний `return` при пустом `value`) не
восстанавливал обычный композит, если редактирование до этого прятало слой
через `previewWithLayerHidden` — канвас оставался показывать спрятанный
слой до следующей случайной перерисовки. Однострочное исправление
(`previewWithLayerHidden(null)` в этой же ветке) устраняет пробел без
переписывания остального.

**Контрактный тест не может проверить `fontSize`/`fontFamily` для `text`**,
и это не пробел инструмента: обе опции читаются только внутри
`commitDraft`, которую вызывает исключительно оверлей — headless-гарнес
теста не рендерит React вообще, значит и `Overlay` никогда не вызывается,
значит коммит для этого теста никогда не случается. Явно пропущено с
комментарием, тем же приёмом, что уже пропускает `"color"`-опции у
рисующих инструментов.

**Проверено вживую**: клик пустым местом создаёт точечный текстовый черновик
в верном месте; печать реального текста; Ctrl+Enter коммитит — создаётся
слой `kind: "text"`, с превью-миниатюрой глифов, именем по первым символам
текста; undo убирает слой; Escape отменяет набор без коммита, ничего не
меняя в документе. Настоящий Ctrl+Enter через `computer`'s эмуляцию
клавиш не сработал (браузерная автоматизация не воспроизводит его так,
чтобы `event.key === "Enter"` совпало с `ctrlKey: true` в React) —
подтверждено прямым `KeyboardEvent` через DOM, что код реагирует верно;
это ограничение метода проверки, не код (тот же класс проблемы, что
`CLAUDE.md` уже фиксирует про `setPointerCapture`). **Не проверено вживую**:
повторный клик по уже существующему текстовому слою (переоткрытие на
редактирование, подстановка его собственных `font`/`color`/`path`) и
режимы `path`/`dynamicCircle`/`dynamicArch`/`dynamicBow` (текст по кривой).

#### `clone`/`spotHeal`/`patch` — последняя треть семёрки, и конец общего `gesture`-рефа

Последние три инструмента старого пайплайна (см. «Второй кандидат по
порядку» в начале этапа 5). С их переносом `gesture` — центральный
изменяемый реф, вокруг которого был построен весь дожатый switch —
потерял последнего писателя: `appendBrushPoint`, `scheduleWorkingRender` и
оба хвоста `handlePointerMove`/`finishGesture`, читавшие `gesture.current`,
стали в буквальном смысле недостижимы (проверено `grep`: ни одного
оставшегося присваивания). Убраны целиком, не оставлены мёртвыми — впервые
за этап 5 сам механизм жеста, а не отдельная его ветка, обнулился.
Тем же заходом ушли `selectionGesture`/`lassoDraft`/`draftKind` (жили

`patch.tsx`) и `patchOffset` (только ради старого оверлея заплатки, теперь
в `patch.tsx`'s собственном `Overlay`).

**`clone`** перенесён с тем же полу-шаговым лагом рисования, что был в
`appendBrushPoint`: сегмент, который реально рисуется на очередной точке —
это `curveStart → pending` *с предыдущего* вызова, а не `curveStart →
point` с этого; `point` и вычисленная midpoint-точка `end` только сдвигают
`curveStart`/`pending` для *следующего* вызова. Не увиденная заново
странность (уже так было, задокументировано в коде честно), а не то, что
эта сессия придумала.

Alt-клик, ставящий источник, и «зарегистрированное» выравнивание (offset
переживает жест) остались на **хосте**, не в состоянии инструмента: перекрестье
и превью-свотч источника — часть шасси мастерской (`updateCloneSourceView`),
рисуются на каждом `pointermove` независимо от активного инструмента, и
читают `sourcePointRef`/`cloneOffsetRef` напрямую. Контракт получил
`ctx.cloneSource`/`ctx.setCloneSource` и `ctx.cloneOffset`/`ctx.setCloneOffset`
как тонкую обёртку над теми же рефами — не новый механизм, имя для уже
существующего.

**`spotHeal`** копит маску-«где лечить» по ходу перетаскивания (растущий
прямоугольник, если жест выходит за старые границы — перенесено
побайтово) и применяет мембрану Пуассона только один раз, на отпускании —
залечивать каждый даб по отдельности зашивало бы швы на нахлёстах.
Контракт получил `ctx.previewSpotHealMask` — тонирование канваса поверх
уже нарисованного, напрямую в канвас, вне React, тем же приёмом, что
`schedulePreview`/`previewWithLayerHidden`; в отличие от них это не буфер
пикселей слоя, а полупрозрачная подсветка того, что накопилось в маске,
поверх обычного композита.

**Найден и закрыт настоящий пробел, не декоративный, а связанный с
безопасностью.** Контрактный тест «не пишет вне всюду-нулевого paintMask»
упал для `spotHeal` — ни `spotHealDab`/`spotHealStrokeSegment`, ни
`spotHealApply`/`copyHealedRegion` не принимают маску выделения вовсе, и
старый переключатель никогда её туда не передавал: точечное восстановление
никогда не уважало выделение. Исправлено не добавлением параметра в четыре
функции движка (что раздуло бы их сигнатуры ради одного вызывающего), а
пересечением накопленной маски-«где лечить» с `ctx.paintMask` в самом
инструменте перед вызовом (`confineHealMask`) — маска лечения уже имеет ту
же форму «область действия», что маска выделения, пересечение двух масок
такой формы не требует третьего параметра ниже по стеку.

**Тем же тестовым прогоном найдены и починены две «мёртвые» опции**, тем же
приёмом, что и у тональных инструментов в прошлой сессии: `spotHeal`'s
`spacing` была объявлена и показана в панели, но `spotHealStrokeSegment`
шагала с зашитой константой 0.18 — параметр добавлен, константа стала
значением по умолчанию, ничего не меняющим для существующих вызовов без
явного аргумента.

**Три опции, найденные тем же тестом, не исправлены, а честно помечены
непроверяемыми одним `fullGesture`** — не пробел в инструменте, пробел в
форме самого теста, тем же классом, что `raster.clone`'s `alignMode` в
прошлой сессии:
- `raster.clone`'s `alignMode` («зарегистрированное»/«нет») различает себя
  только между *двумя отдельными* жестами — на первом жесте без
  предыдущего offset оба варианта считают одно и то же по одной и той же
  причине (`!offset`, не `alignMode`).
- `raster.spotHeal`'s `spacing` имеет что растягивать только на
  Shift-линии (`spotHealStrokeSegment`, которая реально шагает дабами) —
  обычное перетаскивание штампует один даб на коалесцированный сэмпл
  указателя, без собственного шага; `fullGesture` никогда не держит Shift.
- `raster.patch` в фикстуре по умолчанию не имеет выделения — без него
  каждый жест уходит в запасное лассо, а `mode`/`feather` читаются только
  на пути реального заплатывания. Для проверки этих двух `fullGesture`
  теперь сам создаёт для `raster.patch` небольшое выделение (и
  соответствующую `paintMask`, отдельным параметром `drive()` — движок
  `patchFromSelection` иначе тоже молча ничего не делает: он читает свою
  первую маску как «куда класть», а не только как ограничение).

**Проверено вживую, реальным вводом**: Alt-клик по цветному пятну и
последующий мазок штампом переносит цвет в другое место холста (сверено
по пиксельным данным, не только на глаз), undo возвращает как было.
Точечное восстановление подтверждено по журналу истории (несколько
успешных коммитов «Точечное восстановление» после реальных перетаскиваний)
и контрактным тестом, который целенаправленно проверяет именно
пофикшенное ограничение маской (падал до фикса `confineHealMask`, проходит
после) — **не проверено на глаз**, попадание в маленькую тестовую точку
курсором в этой сессии сорвалось трижды подряд из-за плавающих координат
холста при смене масштаба/панелей в узком вьюпорте браузерной панели;
честно засчитано как проверенное данными и тестом, не визуально. `patch`
не проверен вживую вовсе в этой сессии — отложено за нехваткой времени,
честно как пробел, а не молчаливый пропуск.

#### `raster.move` — последний инструмент на старом switch

Перенесён целиком за одну сессию, а не по под-режимам, как изначально
предполагалось («сначала базовое перемещение, потом scale/rotate, потом
quad/warp, потом текст»). Разбиение оказалось структурно невозможным: мост
этапа 3 (`if (catalogueTool?.onPointerDown) {…; return;}`) диспетчерует по
`activeToolId` всё-или-ничего — в момент, когда `raster.move` появляется в
каталоге, старый `switch`-код для этого id становится недостижимым
полностью, для всех под-режимов сразу. Оставить `move` частично на новом
коде между сессиями значило бы держать `main` в состоянии, где часть
под-режимов инструмента тихо не работает — то самое нарушение "никогда не
оставлять `main` сломанным", которое `CLAUDE.md` называет по номеру
инцидента. Формулировка задачи оставляла разбиение на моё усмотрение —
это и есть то усмотрение: перенесено всё сразу, одним файлом
(`environments/raster/tools/definitions/move.tsx`), ~460 строк.

**Перенесено дословно**, не переизобретено: `applyTransformFrame`'s четыре
ветки (`scale`/`rotate`/`quad`/`warp`/`move`), `beginMoveDrag` (бывший
общий хвост `handlePointerDown`), обработка ручек (`quadHandlePoints`,
допуск `11 / zoom`), auto-select с модификатором-инверсией, коммит
клика-мимо-рамки. Само поведение не должно было измениться — изменилась
только форма (владение состоянием у хоста через `toolStates`, а не
замыкание в рефах компонента).

**Куда переехала общая логика**:
- `WARP_GRID`/`regularMesh`/`meshLayerPixels`/`meshSelection` — в
  `@vravio/env-raster` (`packages/env-raster/src/transform.ts`), экспортированы:
  чистая математика по пиксельным массивам, а не что-то специфичное для
  хоста — по правилу трёхслойной дисциплины (раздел 2) она принадлежит
  движку независимо от того, что сейчас у неё один потребитель.
- `quadHandlePoints`/`applyQuadHandleDelta` — остались локальными в
  `move.tsx`: это модель взаимодействия конкретно этого инструмента
  (какая точка — какая ручка), не общая геометрия.
- `enterQuadTransformMode`/`enterWarpTransformMode`/`pendingBounds`/
  `startPendingTransform`/`commitPending`/`empty` — экспортированы из
  `move.tsx` для хоста: `RasterWorkspace.tsx` импортирует их напрямую по
  имени (а не только через `rasterToolById`), потому что три внешних по
  отношению к жесту точки входа — Edit ▸ Free Transform (Ctrl+T), кнопки
  Commit/Cancel в options bar, правый клик "Skew/Distort/Perspective/Warp"
  — не имеют своего pointer-жеста, чтобы завести трансформацию через
  обычный `onPointerDown`. Держать логику одна, читаемая из двух мест,
  показалось честнее, чем заводить вторую, дрейфующую копию того, что
  такое "открыть/закоммитить pending transform" в самом хосте.

**Расширение `ToolContext`** (оба поля — по факту, не заранее):
- `selectedLayers`/`setSelectedLayers` — панели слоёв нужно и то, и
  другое отдельно от `activeLayer`: Shift-клик автовыбора меняет, какой
  слой активен (`setActiveLayer`, без истории, как обычный клик по

  документа: подсветка — это шелл-хром, undo на неё никогда не
  распространялся.
- `scheduleWork` — обобщение уже существовавшего `scheduleTransformFrame`
  (не новая идея, а вынесенная в контракт): RAF-коалесинг для тула, чьему
  `onPointerMove` нужно пересчитать что-то дорогое (весь холст) прежде,
  чем у него будет что отдать в `schedulePreview`. Без него перетаскивание
  ручки scale/rotate/warp читалось как зависание — то же самое измерение,
  которое когда-то дало `schedulePreview`.

**Найден и исправлен один настоящий баг** при проверке вживую: Escape
сбрасывал `pending` в состоянии тула, но не перерисовывал канвас — на
экране оставался последний нарисованный `schedulePreview`-кадр (сжатый/

не срабатывает. Исправление: Escape дополнительно вызывает
`context.previewWithLayerHidden(null)`, тот же метод, что уже использует
`text.tsx` для возврата канваса к обычному композиту.

**Заведомо ложные тревоги при живой проверке в этой сессии**, задокументированы

#### Второй проход: найден и исправлен настоящий баг в scale/rotate/quad/warp

Следующая сессия вернулась к именно тем пунктам, что были помечены выше
как «не проверено» — и первая же точная проверка (координаты ручки
взяты не на глаз, а через `getBoundingClientRect()` самого SVG-элемента
ручки) вскрыла, что ручки **действительно не работали**: рамка после
перетаскивания ручки scale оставалась того же размера, rotate не менял
угол. Причина — не промах координат (как ошибочно предположила
предыдущая сессия), а настоящий баг в `move.tsx`.

`ToolContext.state` — это снимок, снятый один раз в момент, когда
`toolContextFor` строит объект контекста, а не живое значение. `onPointerMove`
считает `nextDrag` (с обновлённым `current`) синхронно и корректно кладёт
его в `context.setState(...)` — но отложенный колбэк, который планирует
`context.scheduleWork(...)`, читал `context.state.drag` заново внутри
себя. Поскольку `context.state` — тот же самый неизменный снимок, это
всегда возвращало значение `drag` **до** обновления в этом же вызове
`onPointerMove`, не после. Когда этот отложенный колбэк реально
срабатывал (через `requestAnimationFrame` — быстрый синтетический драг
вполне успевает дать кадру время сработать до `pointerup`), он тихо
откатывал `drag.current` обратно к тому, чем он был **в начале** того
конкретного вызова `onPointerMove` — для ручки scale/rotate это часто
означало откат прямо к точке захвата самой ручки, отчего рамка
визуально не менялась вовсе, несмотря на настоящий, успешный драг.

Контрактный тест этого не ловит: его harness прогоняет жест синхронно,
без RAF между кадрами (см. `drive()`'s собственный комментарий про это в
`contract.test.ts`) — поэтому баг был доступен только живой проверке.
Исправление: колбэк `scheduleWork` теперь замыкает `nextDrag`,
вычисленный в начале `onPointerMove`, а не перечитывает
`context.state.drag`.

**Дополнительно проверено вживую после исправления**: ручка scale
(перетаскивание нижнего-правого угла корректно меняет W/H кадра и
committed-bounds слоя), ручка rotate (угол в options bar меняется,
видимый поворот содержимого после коммита), вход в Distort через правое
контекстное меню и перетаскивание одного из его углов (видимое
искажение, W/H меняются нелинейно как и ожидается для quad-трансформа),
кнопка Cancel (✕) в options bar (откатывает pending и корректно
перерисовывает канвас к последнему закоммиченному состоянию — тот же
код пути, что и Escape).

Контрактный тест (`contract.test.ts`) не создаёт активное выделение
(кроме `raster.patch`), поэтому ветка плавающего выделения `move` им не
покрывается вовсе — покрыта только живой проверкой выше.

582 теста зелёных (было 575: +7 контрактных проверок на `raster.move`).

этап), ветвлений по `activeToolId` 15 → 7 — но эти семь больше не

#### Третий проход: закрыты все оставшиеся пункты живой проверки `raster.move`, найден и исправлен второй настоящий баг

Прямое продолжение предыдущей подсекции — закрывает ровно то, что там
было честно помечено «не проверено вживую»: ручки warp отдельно от
quad, Skew и Perspective отдельно от уже проверенного Distort,
трансформация текстового слоя (включая `text-transform-preview`
`canvas`), коммит pending-трансформации при переключении слоя в панели
слоёв.

**Warp, Skew, Perspective — все три проверены реальным вводом** (не на
глаз: координаты каждой ручки взяты через `getBoundingClientRect()`
самого SVG-элемента в момент перед перетаскиванием, а не один раз в
начале сессии, потому что канвас панорамировался между проверками).
Warp: перетаскивание одной внутренней точки 4×4-сетки видимо искажает
пиксели вокруг неё, коммит сохраняет искажение, undo возвращает
исходный крест. Skew: перетаскивание ручки середины верхнего края
превращает прямоугольную рамку в параллелограмм (единственная ось
сдвига, как и должно быть — в отличие от Distort/Perspective), контент
сдвигается вместе с рамкой. Perspective: перетаскивание одного угла
внутрь тянет оба соседних (`hPartner`/`vPartner`) в противоположную
сторону, давая трапецию, а не общий четырёхугольник (чем Perspective и
отличается от Distort) — все три подтверждены и по кадру перетаскивания
(живой предпросмотр), и по результату после Enter.

**Трансформация текстового слоя — проверена и вскрыла настоящий баг,
не связанный со снимком `context.state`.** Первая попытка (Ctrl+T на
только что набранном текстовом слое, затем клик мимо рамки без
перетаскивания — то есть коммит tождественной трансформации) дала
пустой результат: слой на канвасе исчез, хотя `document.state`
показывал корректные, ненулевые пиксели текста внутри заявленных
`layer.bounds`. Причина — не второй случай «снимок против живого
значения» (первая гипотеза, которую стоило проверить по совету плана;
не подтвердилась), а более простой и более серьёзный баг: `commitPending`'s
ветка для `pending.text` писала результат `renderTextLayerPixels(...)`
(буфer размером с **весь канвас**, 1920×1080×4) прямо в `target.pixels`,
минуя `setLayerPixels` — единственную функцию, которая обрезает такой
буфер до непрозрачных границ и синхронно обновляет `layer.bounds`
(приём, вокруг которого построена вся оптимизация «слой хранится в
своих границах», `CLAUDE.md` §1 и §5). В результате `layer.bounds`
оставался **старым**, маленьким (например, `153×35`), пока
`layer.pixels` внезапно становился документного размера — и
компоузер (`render.ts`, некорректный для `wholeCanvas === false`
путь) читал этот буфер, как будто он **уже обрезан** до
`layer.bounds`, беря `sourceWidth = layer.bounds.width` и индексируя в
буфер, размер которого на самом деле в разы больше. Результат —
чтение из полностью не тех байт: не мусор на экране (это было бы
заметно сразу), а тихо пустой прямоугольник, потому что почти все
вычисленные индексы либо выходят за пределы реального содержимого,
либо попадают в прозрачные области того же большого буфера. Первый же
`git blame`-подозреваемый — единственное место в `move.tsx`, что вообще
пишет `target.pixels` для текстовой ветки, и единственное место кодовой
базы, делающее это в обход `setLayerPixels` (проверено `grep`'ом по
`environments/raster/` и `RasterWorkspace.tsx` — других таких мест нет).

Починка: `target.pixels = renderTextLayerPixels(...)` заменено на
`setLayerPixels(target, renderTextLayerPixels(...), afterDoc.width,
afterDoc.height)` — тот же приём, что уже использует `text.tsx`'s
`commitDraft` при первом создании текстового слоя (откуда и видно, что
исходная типизация просто не сработала одинаково в двух местах,
делающих семантически одно и то же). Проверено вживую после
исправления, реальным `left_click_drag`: масштабирование текстового
слоя (перетаскивание угловой ручки, `W/H` меняются, `layer.bounds`
после коммита `212×87`, `layer.pixels.length` = `212·87·4` — совпадает
день в день) и поворот того же слоя на `152.7°` тем же жестом за ручку
rotate — оба коммита дали видимо корректный, читаемый повёрнутый/
увеличенный текст на канвасе и в миниатюре слоя, не пустой прямоугольник.
Живой предпросмотр через `text-transform-preview canvas` тоже
подтверждён отдельно: во время самого перетаскивания (до отпускания
кнопки) канвас показывает увеличенный/повёрнутый кроп текста заметно
раньше коммита — то есть сам предпросмотр всегда был корректен, ломался
только итоговый закоммиченный буфер.

**Коммит pending-трансформации при переключении слоя в панели слоёв —
подтверждено.** Открыт pending на текстовом слое (перетаскивание рамки
целиком, без ручки — обычный `move`-режим), затем, не отпуская
pending, клик по строке другого слоя в панели «Слои». `activeLayerId`
переключился на кликнутый слой, а `previousActiveLayerId`-эффект
(`RasterWorkspace.tsx:723`) вызвал `commitPending` для оставленного
pending: `layer.bounds` того текстового слоя после переключения точно
совпал с координатами, которые показывал X/Y/W/H readout непосредственно
перед кликом по панели (`370,770,210×163`), и `pixels.length` снова
согласован с `bounds` — то есть тот же самый чинённый путь `commitPending`
отработал правильно и здесь, поскольку это одна и та же функция.

**Побочно уточнён метод измерения координат в этой сессии.** Скриншот
Browser pane и `getBoundingClientRect()` живут в разных системах
координат: скриншот — это CSS-вьюпорт (`window.innerWidth/innerHeight`),
отмасштабированный до бюджета токенов (в этой сессии — `846×794` →
`800×750`, коэффициент ≈`0.9456`/`0.9446` по осям), а не размер канваса
и не физические пиксели (`devicePixelRatio` тут ни при чём). Клик по
координате, снятой из `getBoundingClientRect()` без этого пересчёта,
промахивается на сопоставимую с самой ручкой величину. Правило для
следующей сессии: всегда домножать координаты `getBoundingClientRect()`
на `screenshot.width / window.innerWidth` (и то же для Y), а не
предполагать совпадение один-в-один.

Типы чистые по всем четырём пакетам (`apps/web`, `packages/env-raster`,
`packages/kernel`, `packages/env-vector`), 582 теста зелёных (без
изменений в счётчике — эта сессия не добавляла новых тестов, только
живую проверку и один построчный фикс в уже покрытом контрактным тестом
файле; `move.tsx`'s контрактный тест не пишет текстовые слои достаточно
специфично, чтобы поймать этот конкретный баг — он завязан на реальный
композитинг несовпадающих `bounds`/`pixels`, чего headless-гарнес не
проверяет, ровно как и в прошлой сессии с warp/quad).

#### Вектор — 6 инструментов, перенесены все разом, старая логика удалена в тот же заход

`packages/env-vector` (289 строк) и вектор-часть UI (`VectorWorkspace.tsx`,
376 строк до переноса) оказались на порядок меньше растровых — шесть
инструментов делят один жест на одном `<svg>`, а не тридцать делят канвас.
Поэтому, в отличие от растра (этап 3: мост + один тул, этап 5: остальные
двадцать девять по одному через много сессий), здесь мост спроектирован и
все шесть инструментов перенесены одним заходом, а старый `onPointerDown`/
`onPointerMove`/`onPointerUp` (рефы `draft`/`pathDraft`/`penHandle`/
`nodeDrag`, состояние `selectedNode`, `hitTestNode`, `shapeToolKinds`,
`style()`) удалён в этом же изменении — держать это на несколько сессий
ради шести инструментов было бы искусственным дроблением, а не
осторожностью.

**Контракт — `environments/vector/tools/types.ts`, `ToolContext`/
`VectorToolDefinition` — списан с `VectorWorkspace.tsx`'s реальных ветвлений,
тем же приёмом, что и растровый в своё время, но по устройству другой не
из прихоти:**

- **`mutate(fn)` — легальный канал живой записи в документ во время
  жеста**, не нарушение правила. У растра любая прямая запись в
  `context.document` — то, что ловит контрактный тест; у вектора
  `kernel.documents.update(...)` вызывался и до переноса на каждый
  `pointermove` (перетаскивание фигуры — десятки живых записей в секунду,
  один шаг истории на отпускание), так что растровое «нельзя писать мимо
  commit» здесь неприменимо по конструкции, а не забыто. `mutate`
  называет это прямо и контрактный тест вектора (см. ниже) не пытается
  запретить то, что является частью контракта.
- **`commitDrag(before, label)`** — тонкая обёртка над уже существовавшим
  `commitVectorDrag`: один шаг истории для жеста, чей эффект уже живёт в
  документе через повторные `mutate`. Дешевле растрового `commit` не
  зря — дерево фигур, не пиксельный буфер, ни маски выделения, ни
  ревизии ассета.
- **`changeDocument(label, mutate)`** — обёртка над `changeVectorDocument`,
  для тула без фазы живого перетаскивания (`vector.text`'s одиночный клик,
  `vector.nodes`'s удаление точки).
- **`ToolPointer` получил `detail`** — растровому ни одному тулу не
  понадобилось различать одиночный и двойной клик, `vector.pen` эту
  разницу читает напрямую с нативного `PointerEvent.detail`, чтобы понять,
  что двойной клик завершает контур.
- **`capturePointer` не перенесён.** В пре-портовом коде не было ни
  одного вызова `setPointerCapture` — SVG вектора занимает весь канвас, а
  `onPointerLeave={onPointerUp}` коммитит жест при выходе курсора вместо
  того, чтобы зависать. Контракт называет это явно в комментарии к
  `onGestureEnd`, а не добавляет неиспользуемый метод «на всякий случай».

там делать нечего. Пункт оставлен невыполненным сознательно: решение за
владельцем проекта, выдумывать поведение здесь нельзя.

**Найдено живой проверкой: правка, отклонённая правилом, оставалась на
экране.** Кисть рисует прямо в канвас по ходу жеста (`schedulePreview`,
мимо React — это оплаченная оптимизация, а не небрежность), а вето в
`commitPixels` только писало диагностику и выходило. Ревизия документа при
вето не меняется, значит эффект тайлового кэша не перезапускается, и мазок
оставался висеть на экране как настоящий: `layer.bounds` доказывал, что в
документ не попало ничего. Это то же нарушение «одной двери», что и
`b7c1f84`, только зеркальное — экран показывал то, чего не было. Вето
теперь перерисовывает канвас из `state`.

**Причина, по которой до вето вообще доходило: этап 5 увёл инструменты
из-под проверки блокировок.** В `RasterWorkspace.tsx` стояла проверка с
комментарием «блокировки проверяются один раз здесь, а не в каждом
инструменте», но она физически ниже диспетчеризации каталога, которая
делает `return`. Каждый перенесённый инструмент читал вместо неё
`activeLayer.locked` — это только Lock All, и слой с одним лишь
«закрепить пиксели» жест принимал. Шесть инструментов чинит общий
`tools/lock-guard.ts`; `shape.tsx` — обоснованное исключение, он создаёт
свой слой, а не пишет в активный. Enforcement остаётся за правилами:
`locksRefuse` — это инструмент, отказывающийся начинать жест, который всё
равно не будет принят, чтобы отказ был виден сразу, а не мазком, который
пользователь увидел и потерял.

Тесты: 13 контрактных на правила и движок, 5 на «одну дверь» (сканируют
исходник — свойство структурное), 1 на то, что сырой флаг `locked` остался
только в `shape.tsx`. Каждый проверен на невакуумность: при снятой правке
падает именно он. Типы чистые по четырём пакетам, 631 тест зелёный.

Живая проверка в браузере: обычный мазок проходит невредимым; мазок через
границу выделения обрезан ровно по ней (выделение x 51..379, покрашено
214..379 при жесте до x≈684 — по `getBoundingClientRect`, не на глаз); кисть,
заливка и осветлитель на слое с «закрепить пиксели» отказывают сразу, каждый
со своей причиной в диагностике; снятие блокировки возвращает рисование
(`bounds` 450×24, `pixels.length` 43200 = 450·24·4). Перерисовку по вето
живьём вызвать больше нельзя — после исправления ни один инструмент до вето
не доходит; она проверена тестом и наблюдалась живьём до починки.

**Каталог команд.** Все 80 регистраций уехали из одной 327-строчной
`ensureCommandsRegistered` в файлы, которые находит `commands/registry.ts`
тем же `import.meta.glob`. Общие команды — в `commands/definitions/`,
остальные — в `environments/<среда>/commands/definitions/`. Гранулярность —
семья на файл, а не команда на файл: инструмент занимает от пятидесяти до
четырёхсот строк, команда — одну, а семья делит хелперы и категорию;
свойство «новую семью не надо вписывать в длинную функцию» сохранено.

Сеть под переносом — `commands/catalogue.test.ts`: 80 строк
`id|shortcut|scope|category`, снятых с работающего приложения **до**
переноса. Не снапшот: снапшот, который перегенерируется по `-u`, записал бы
то, что получилось после рефакторинга, то есть ровно проверяемое.

**Про три поля 4.3 честно.** `surfaces` заполнен и работает: командная
часть контекстного меню слоя собирается из каталога. `args` и
`neverRecord` объявлены в контракте для сценариев этапа 9 и **никем не
читаются** — это сказано и в типе, и здесь, чтобы не выглядело работающим.
`neverRecord` проставлен там, где смысл уже ясен (undo/redo, палитра,
настройки).

**Генерация всей строки меню — отдельная задача, не сделана.** Разбор:
меню в `App.tsx` захардкожено массивами `[label, shortcut, handler]` и уже
разошлось с реестром (Export в меню на Ctrl+Shift+E при
зарегистрированном Mod+Shift+Alt+W; «Merge Down» в меню отключён при
рабочей `layer.mergeDown`). Но простой генерации мешают две вещи, и обе
надо решать явно: категории команд не совпадают с меню (есть категории
Select, View и 3D, а таких меню в строке нет — их команды сегодня живут
только в палитре), и около двадцати пунктов меню командами ещё не
являются («Импорт…», «Печать…», «Умное кадрирование», «Водяной знак»,
«Стиль слоя…», начертания текста, галерея фильтров), плюс несколько
пунктов-заглушек, отключённых навсегда. Генерировать «как есть» значит
либо потерять рабочие пункты, либо насыпать в меню лишнего. Правильный
следующий шаг — довести эти пункты до команд и добавить недостающие меню;
это решение о продукте, а не о переносе.

**Найден и починен баг, роняющий приложение** (жил до этой сессии):
кнопка «Новая группа» создаёт пустую группу и делает её активной, а
`ungroupLayer` для группы без детей оставлял `activeLayerId` на группе,
которую сам же удалял. `activeRasterLayer` на висячем id бросает
исключение, экран пустой, а состояние успевало уехать в автосохранение —
перезагрузка не спасала. Выделение теперь наследует сосед.

**Каталог окон.** `raster-core-panels/` и `vector-core-panels/` были одним
каталогом, скопированным дважды: одинаковые типы, реестр, рантайм и две
пары событий, так что починка одного молча оставляла второй позади. Теперь
`environments/<среда>/windows/definitions/` и один реестр, берущий среду из
пути — панель под `environments/vector/` векторная, и написать иначе
нельзя. Ключи хранения не менялись, иначе у всех, кто уже пользовался
приложением, сбросилась бы раскладка. Поля `modals` и `contextMenu` из 4.2
объявлены и пока не читаются, о чём сказано в самом типе.

Список «Окна» — свой на среду и наконец с галочками: галочка была, но
приклеивалась к строке `"✓ Properties (Свойства)"` целиком, а
`localized()` возвращает только скобочную половину, то есть по-русски
галочек не показывалось вообще.

**Второй найденный баг:** выключение векторной панели «Цвет» стирало
растровую. Растр и вектор называют панели одинаково (`properties`,
`layers`, `history`, `color`), а сохранение раскладки определяло среду
вопросом «есть ли в этом каталоге такой id». Среду теперь даёт активный
документ. Совпадение id закреплено тестом как ловушка, а не как ошибка:
каждой среде нужен свой «слои».

**Каталог модальных окон.** `modals/` с реестром, стеком и хостом; окно
вызывается по id. Сделаны три с настоящими вызывающими: `confirm` (общий —
`RasterizeConfirmDialog` был им же с одним вопросом внутри), `error` и
`new-document`.

`error` закрыл настоящую дыру: несколько отказов писали диагностику и
делали `return`, так что брошенный в окно битый файл не давал ровно
ничего, а причина лежала в журнале за меню «Справка». Особенно плох был
отказ сохранения — человек уходит, считая, что работа на диске.

**`progress` не сделан намеренно.** Занятость уже показывает `BusyCursor`:
курсор со спиннером, который ничего не блокирует и появляется с задержкой,
чтобы быстрая операция не мигала текстом. Блокирующее окно поверх тех же
операций было бы ухудшением, а решать, какие операции достойны блокировки,
— вопрос к продукту. Пункт оставлен владельцу, как и `clipping-mask-bounds`
в этапе 6.

### Этап 8. Панель инструментов

Первое видимое пользователю изменение.

- [x] Перетаскивание инструментов
- [x] Кнопка `(...)`: показать/скрыть, группировка
- [x] Раскладка панели переживает перезагрузку, своя на среду
- [x] Сброс к раскладке по умолчанию

Панель рисуется из раскладки (`toolbar/layout.ts`), а не из жёсткого
`rasterToolGroups`: группы в порядке следования, в каждой — инструменты,
делящие одну ячейку, плюс список скрытых. У панели, которую никто не
трогал, вид прежний — умолчание берётся из той же группировки Photoshop в
`tools.ts`. Редактор открывается по id через каталог модальных окон этапа
7, то есть первый же новый потребитель того механизма оказался не
выдуманным.

**`reconcileLayout` — то место, где это тихо ломается.** Раскладка
пишется один раз и читается годами, а каталог инструментов меняется под
ней. Инструмент, не попавший ни в одну группу, не рисует никто: новый
инструмент просто не появился бы у всех, кто хоть раз переставлял панель,
и выглядело бы это как баг инструмента, а не раскладки. Пустая группа —
дырка в панели, дубль — вторая ячейка, из которой нельзя выбрать. Всё это
в тестах, включая «скрытый инструмент не воскресает видимым».

**Тест нашёл ошибку на единицу.** Индекс щели при перетаскивании надо
сдвигать, только если схлопнувшаяся группа была *выше* цели, а не при
любом схлопывании: инструмент, перетащенный вверх, промахивался на одну
ячейку. Ветка «в группу» страдала тем же и теперь опознаёт цель по
соседнему инструменту, а не по индексу, который перестановка сдвигает.

**Два решения приняты по итогам живой проверки, а не заранее.**

Скрытый инструмент **сохраняет шорткат**: скрытие разгружает панель, а не
отнимает инструмент, и молча ломать знакомую клавишу хуже тесной панели.
Но тогда при нажатии клавиши ни одна ячейка не подсвечена — панель
показывает «ничего не выбрано» при явно активном инструменте, то есть
врёт. Подсвечивается кнопка `…`, подсказка называет инструмент: это и
честный ответ на «какой сейчас?», и ровно то место, куда идти, чтобы
вернуть его на панель.

Сохранение раскладки, совпадающей с умолчанием, **стирает** запись, а не
пишет её: иначе сразу после сброса кнопка «Сбросить по умолчанию»
оставалась бы доступной и предлагала отменить несуществующую настройку.

### Этап 9. Сценарии

- [x] Запись команд с аргументами
- [x] Чёрный список: `neverRecord` + всё из `script.*` и `edit.undo/redo`
- [x] Воспроизведение с остановкой на ошибке
- [x] Окно «Сценарии» в каталоге окон
- [x] Команды `script.record`, `script.stop`, `script.play`, `script.delete`
- [x] Тест: запись сценария не записывает саму себя

**Аргументы перестали быть объявлением.** `Command.execute` принимает
`CommandArgs`, реестр проверяет их по схеме определения (`coerceArgs`) на
входе: команда никогда не защищается сама от сценария, отредактированного
руками или записанного старой сборкой, а команда со схемой читает
аргументы без единого `??`.

Первым аргумент получило умное кадрирование — и это не выдуманный повод.
Три захардкоженных пункта меню стали одной командой `image.smartCrop` с
аргументом `ratio`, меню строится из списка её же соотношений, четвёртое
(3:2) добавилось строкой данных. Заодно закрыт один из тех «около двадцати
пунктов меню, которые ещё не команды», о которых сказано в этапе 7.

**Чёрный список — три отказа об одном:** записать то, воспроизведение чего
подействует на запись, а не на документ. `neverRecord` (поле этапа 7
получило читателя), весь префикс `script.` (забытый флаг у новой команды
не должен давать сценарий, взводящий рекордер вместо работы) и
`edit.undo`/`edit.redo` — записанная отмена отменяет то, что сделало
*воспроизведение*, то есть съедает шаг, который пользователь хотел
оставить. Отмены во время записи — это правки записи, а не её часть.

**Остановка, а не пропуск,** потому что шаги не независимы: «выделить,
залить, снять выделение» при провалившемся выделении зальёт весь слой.
Четыре причины отказа различаются, потому что чинятся по-разному: команды
нет, отказала `isEnabled`, аргументы не подходят под схему, бросила.

Рекордер подписан на сам реестр команд, а не на вызывающего: подписка на
одного вызывающего молча писала бы неполный сценарий, потому что команда
приходит и шорткатом, и из меню, и с кнопки панели.

**Граница того, что такое сценарий здесь, выбрана явно:** шаг — это id и
аргументы, без снимка состояния и без координат. Он воспроизводит
*решения*, а не их результаты, поэтому записанный на одном документе
делает осмысленное на другом. Обратная сторона: работа инструментами
(мазки, перетаскивания) в сценарий не попадает — она идёт не через
команды. Это ограничение по построению, а не недоделка.

**Найдено по дороге:** `diagnostics.ts` бросал ReferenceError на
`window.dispatchEvent` вне браузера — сквозь того, кто как раз пытался
сообщить о проблеме. Модуль, обещающий «диагностика никогда ничего не
ломает», ломал именно то, что ему запрещено в первую очередь.

**Замечание о стоимости, не о правильности:** умное кадрирование на
документе 1920×1080 уронило вкладку на этой машине (композит всего
документа плюс перебор областей на главном потоке). Код при переносе не
менялся — сравнение с оригиналом показывает только переименования, — так
что это дошедшая сюда цена самой операции, а не регрессия. На 400×300
работает. Кандидат в Worker при переходе к этапу 6.2 сквозных задач.

## 7. Риски

| риск | как снимаем |
|---|---|
| Большой разрыв ломает всё | Мост на этапе 3: старый и новый путь живут вместе; переносим по одному |
| Атомарность съедает производительность | Граница из раздела 2; бенчмарк-порог с этапа 0 |
| Контракт инструмента оказался неполным | Он выведен из 49 реальных ветвлений, а не придуман; уточняется на трёх инструментах до массового переноса |
| Правило можно обойти | `ctx.commit` — единственная дверь; тест на тождество объекта |
| i18n переделывать дважды | Этап 1 идёт до разноса |
| macOS не запустит сборку | Подпись и нотаризация вписаны в этап 12, а не оставлены на потом |
| Плагин вешает интерфейс | Worker, не главный поток |

## 8. Что считается успехом

1. Новый инструмент — **один файл** в `environments/<среда>/tools/definitions/`.
   Ни одной правки в другом месте.
2. Новое окно, команда, правило, коррекция, плагин — то же самое.
3. Новая среда — **один подкаталог** с `environment.ts`.
4. `RasterWorkspace.tsx` ≤ 400 строк; ни одного `activeToolId === "..."`.
5. Ни одна цифра из раздела 1 не ухудшилась.
6. Приложение открывается в браузере, `.exe` на Windows и `.app` на macOS из
   одного кода.
